#### 目标

*   静态类型（static typing）

冰雹序列（hailstone sequence）
------------------------------------------------------------------------------------------------------

我们以**冰雹序列（hailstone sequence）**作为贯穿全课的示例，其定义如下：从某个正整数 _n_ 开始，若 _n_ 为偶数，则下一项为 _n/2_；若为奇数，则下一项为 _3n+1_。序列终止于 1。示例如下：

2, 1  
3, 10, 5, 16, 8, 4, 2, 1  
4, 2, 1  
2 n, 2 n-1 , … , 4, 2, 1  
5, 16, 8, 4, 2, 1  
7, 22, 11, 34, 17, 52, 26, 13, 40, …？（它会在哪停下？）

由于奇数规则，序列可能在下降前上下“弹跳”，因此得名“冰雹”——正如冰雹在云里反复升降，直到重量足够才坠落地面。目前猜想所有正整数最终都会降到 1，但这仍是[悬而未决的问题](https://en.wikipedia.org/wiki/Collatz_conjecture)。

> **背景扩展：** 该猜想又称科拉兹猜想（Collatz conjecture），自 1937 年提出以来尚未被证明或证伪，成为数学界著名的“简单表述、难以证明”问题之一。
### 计算冰雹序列

下面这段代码用于计算并打印某个起始 _n_ 的冰雹序列（hailstone sequence）。我们并排给出 JavaScript 与 Python 版本以便对比：

```python
# Python
n = 3
while n != 1:
    print(n)
    if n % 2 == 0:
        n = n / 2
    else:
        n = 3 * n + 1

print(n)
``````ts
// JavaScript (or TypeScript, this code works in both languages)
let n = 3;
while (n !== 1) {
    console.log(n);
    if (n % 2 === 0) {
        n = n / 2;
    } else {
        n = 3 * n + 1;
    }
}
console.log(n);
```


JavaScript 表达式与语句的基本语义与 Python 非常接近。例如，`while` 和 `if` 关键字的行为一致。

有几点语法值得注意：

*   JavaScript 要求 `if` 和 `while` 的条件必须用括号包裹。
*   JavaScript 语句以分号结尾。技术上可省略，因为 JavaScript 会自动在行末补充分号，但这条规则存在隐蔽陷阱，可能导致意外行为和 bug，因此始终手写分号是良好实践。
*   JavaScript 用花括号标记代码块，而非缩进。但你仍应始终缩进块内代码——尽管 JavaScript 会忽略多余空格。编程是一种沟通，你不仅要让编译器理解，也要让人类理解。人类需要缩进。我们稍后还会回到这一点。

你可能还注意到 JavaScript 版本使用 `===` 和 `!==`，而 Python 使用 `==` 和 `!=`。这是因为 JavaScript 的 `==`/`!=` 会进行各种自动类型转换，试图让左右两边的值可比。例如 `0 == ""` 在 JavaScript 中为真，这令人惊讶且困惑。三等号版本更安全、行为更可预测：`0 === ""` 为假。优秀的 JavaScript 程序员只会使用 `===` 和 `!==`。这是从 Python 迁移时的潜在陷阱。

类型
----------------------------------------------------------------------------

但本课程严格来说并不使用 JavaScript，而是使用 **TypeScript**，它在 JavaScript 基础上增加了在程序中声明类型的能力。此处我们可以指定变量 `n` 的类型为 `number`：

```ts
let n: number = 3;
```


**类型（type）** 是一组值，以及可对这些值执行的操作。

TypeScript 内置若干类型，包括：

*   `number`，表示整数与浮点数
*   `boolean`，表示真或假
*   `string`，表示字符序列

**操作（operations）** 是接受输入并产生输出（有时也修改值本身）的函数。操作语法多样，但无论写法如何，我们都将其视为函数。Python 或 TypeScript 中操作的几种不同语法：

*   **作为操作符**。例如 `a + b` 调用操作 `+ : number × number → number`  
  （记法中：`+` 为操作名，`number × number` 是箭头前的两个输入类型，`number` 是箭头后的输出类型。）

*   **作为函数**。例如 `Math.sin(theta)` 调用操作 `sin: number → number`。此处 `Math` 并非对象，而是包含 `sin` 函数的类。

*   **作为对象方法**。例如 `str1.concat(str2)` 调用操作 `concat: string × string → string`。

*   **作为对象属性**。例如 `str.length` 调用操作 `length: string → number`。注意 `str.length` 后无括号。

对比 TypeScript 的 `str.length` 与 Python 的 `len(str)`：两者都是“取字符串并返回其长度”的同一操作，只是语法不同。

某些操作被**重载（overloaded）**：同一操作名用于接受不同类型参数的函数。操作符 `+` 在 TypeScript 中被重载。用于数字时，`5 + 3` 得 `8`；用于字符串时则做拼接，`"5" + "3"` 得 `"53"`。重载不限于操作符，方法与普通函数也可重载。大多数编程语言都有一定程度的重载。

静态类型
--------------------------------------------------------------------------------------------

TypeScript 是一门**静态类型（static typing）**语言。变量在**编译期**（程序运行前）被赋予类型，编译器据此推导含这些变量的表达式类型。若 `a` 与 `b` 被声明为 `number`，则编译器得出 `a+b` 也是 `number`。VS Code 环境在你敲代码时就完成这一过程，因此许多错误在输入阶段即可发现。

相比之下，JavaScript 与 Python 是**动态类型（dynamically-typed）**语言，因为这类检查被推迟到**运行时**（程序执行期间）。

静态类型是一种**静态检查（static checking）**，即在编译期查错。Bug 是编程的噩梦。本课程许多理念旨在从代码中消灭 bug，静态检查是我们看到的第一个手段。静态类型能阻止一大类 bug：确切地说，是因对错误类型参数执行操作而引发的 bug。如果你写下如下破代码：

```ts
"5" * "6"
```


试图将两个字符串相乘，静态类型会在你仍编程时捕获该错误，而非等到执行到这一行才报错。

> **学习批注：** 静态检查如同拼写检查器：写完就能标红，避免把 typo 留到运行时才爆炸。
### 编译时的静态类型，运行时的动态类型

静态类型声明在编译阶段用于执行静态检查（static checking）。增加静态类型并不会改变程序在运行时的行为仍由实际值驱动这一事实。在冰雹序列（hailstone sequence）程序中，如果我们声明 `let n: number = 3;` 来指定 `n` 的静态类型，运行时的初始值依然是 `3`，而不是任何其他 `number`。当静态类型可能对应多种运行时类型时，我们必须牢记这一区别：一个静态类型为 `Animal`（假设）的变量，运行时实际上可能是 `Dog`、`Fish` 或 `SpottedOwl`。

事实上，TypeScript（与许多静态类型语言一样）在编译完成后会**丢弃**静态类型信息。TypeScript 编译器生成的是什么？JavaScript！下面是一段类型正确的 TypeScript 代码及其生成的 JavaScript：

```ts
// TypeScript to compile
function hello(name: string): string {
    return 'Hi, ' + name;
}
let greeting: string = hello('types');
``````javascript
// JavaScript generated
function hello(name) {
    return 'Hi, ' + name;
}
let greeting = hello('types');
```


> **学习批注：**  
> 静态类型只是开发阶段的“安全带”，编译后就被脱掉，运行时完全靠值自己“裸奔”。  
> 类比：就像登机前查身份证，起飞后空乘不再核对，乘客想换座位也没人拦。
### 动态类型语言中的静态类型支持

就像 TypeScript 给动态类型的 JavaScript 增加了静态类型一样，Python 也有扩展支持静态类型。Python 3.5 及以上版本允许在代码中声明 [类型提示](https://www.python.org/dev/peps/pep-0484/)，例如：

```python
# Python function declared with type hints
def hello(name:str)->str:
    return 'Hi, ' + name
```


声明的类型可以被像 [Mypy](http://mypy-lang.org/) 这样的检查器用来在**不运行代码**的情况下静态发现类型错误。

向 Python、JavaScript 这类动态类型语言添加静态类型，反映了软件工程师的普遍共识：**静态类型**（static typing）对构建并维护大型软件系统至关重要。本文其余部分乃至整门课程都将展示支持这一观点的理由。

在动态类型语言里加静态类型，还能启用一种叫 [渐进类型](https://en.wikipedia.org/wiki/Gradual_typing)（gradual typing）的编程方式：部分代码带静态类型声明，部分省略。渐进类型让小规模实验原型更平滑地成长为大型、稳定、可维护的系统。

静态检查、动态检查、无检查
------------------------------------------------------------------------------------------------------------------------------------------------------------

可以把语言提供的自动检查分成三类：

*   **静态检查**（static checking）：程序尚未运行就自动发现 bug。
*   **动态检查**（dynamic checking）：代码执行时自动发现 bug。
*   **无检查**：语言根本不帮你找错，你得自己盯，否则就得到错误结果。

显然，**静态**优于**动态**，**动态**优于**无**。

以下是各阶段可能捕获的错误经验法则。

**静态检查**可捕获：

*   语法错误，如多余标点或拼写多余单词。即便 Python 这类动态类型语言也会做此静态检查；缩进错误在程序启动前就会报。
*   拼写错误的名称，如 `Math.sine(2)`。（正确拼写为 `sin`。）
*   参数数量不对，如 `Math.sin(30, 20)`。
*   参数类型不符，如 `Math.sin("30")`。
*   返回类型不符，如 `return "30";` 与声明返回 `number` 不符。

**动态检查**可捕获，例如：

*   特定非法参数值。表达式 `x/y` 当 `y` 为零时出错，而其他值则合法；因此除零不是静态错误，编译期无法预知 `y` 是否为零，但运行时可捕获；Python 会抛 `ZeroDivisionError`。
*   非法转换，即具体值无法按目标类型表示。例如 Python 中 `int("hello")` 会抛 `ValueError`，因为字符串 `"hello"` 无法解析成十进制整数。
*   索引越界，如字符串或数组使用了过大的下标；Python 中 `"hello"[13]` 会抛 `IndexError`。
*   在无效对象引用上调用方法（Python 报 `None`，TypeScript 报 `undefined` 或 `null`）。

静态检查只能发现与**类型**相关的错误——即变量被允许取的值集合（在 TypeScript 等静态类型语言中编译期已知），但通常无法发现来自该类型的**某个具体值**的错误。

你可能注意到，上面动态检查的例子大多来自 Python。那 TypeScript 的动态检查呢？TypeScript 负责静态检查，但运行时行为完全由 **JavaScript** 提供，而 JavaScript 设计者决定对许多情况**不做检查**。于是，当字符串或数组索引越界时，JavaScript 返回特殊值 `undefined`，而非像 Python 那样抛错；除零时返回表示无穷的特殊值，也不抛错。**无检查**让 bug 更难发现，因为这些特殊值会继续参与后续计算，直到在离原错很远的地方才暴露故障。

> **学习批注：** JavaScript 的“静默失败”策略（如越界返回 `undefined`）会把错误传播到下游，增加调试难度；写代码时应主动加入边界检查或使用严格模式。
### 意外：`number` 并非真正的数字

TypeScript（与许多其他编程语言一样）还有一个陷阱：其数值类型在某些边界情况下并不像我们熟悉的整数或实数那样表现。因此，一些本应被动态检查（dynamic checking）的错误根本没有被检查。以下是 TypeScript 中隐藏的几个陷阱：

*   **整数精度有限**。TypeScript 中的所有数字都是浮点数（floating-point），这意味着大整数只能近似表示。范围在 −2^53 到 2^53 之间的整数可以精确表示，但超出该范围后，浮点表示只保留最高有效位。如果你尝试对 2^60 进行自增会发生什么？你会得到同样的数字：`2**60 + 1 === 2**60`。因此，这里本应出现动态错误（因为计算结果无法正确表示），却反而给出了错误答案。

这些可表示整数的上下限已作为内置常量提供：`Number.MAX_SAFE_INTEGER` 和 `Number.MIN_SAFE_INTEGER`。

> **学习批注：** 在 JavaScript/TypeScript 中，`Number.MAX_SAFE_INTEGER` 为 9007199254740991（即 2^53−1），超过此值后 `n+1 === n` 可能为真，导致“计数器失效”这类隐蔽 bug。

*   **特殊值**。`number` 类型包含几个非实数的特殊值：`Number.NaN`（“非数字”）、`Number.POSITIVE_INFINITY` 和 `Number.NEGATIVE_INFINITY`。当你对某些 `number` 执行本应触发动态错误的操作（如除以零或对负数开平方）时，会得到这些特殊值而非异常。如果继续计算，最终结果将不可靠。

*   **溢出与下溢**。极大或极小的数也无法表示。`Number.MAX_VALUE` 约为 10^308，`Number.MIN_VALUE` 约为 10^−324。当计算结果超出这一有限范围时，会静默地*溢出*（变成 `POSITIVE_INFINITY` 或 `NEGATIVE_INFINITY`）或*下溢*（变成零）。

> **背景扩展：** IEEE-754 标准规定，超出上限得 `Infinity`，低于最小正数得 `0`，而 `NaN` 会污染后续所有运算，导致“垃圾进，垃圾出”。在财务或科学计算中，这类静默失败尤其危险。
#### 阅读练习

让我们尝试一些带有 bug 的代码示例，看看它们在 TypeScript 中如何表现。这些 bug 会被**静态检查（static checking）**、**动态检查（dynamic checking）**捕获，还是根本不会被发现？

1

```ts
let n: number = 5;

数组
------------------------------------------------------------------------------

让我们修改冰雹序列（hailstone sequence）的计算，使其将序列存储在数据结构中，而不仅仅是打印出来。

为此，我们可以使用**数组（array）**类型。数组是可变长度的同类型元素序列，类似于 Python 的列表。以下是声明数字数组并创建空数组的方式：

```ts
let array: Array<number> = [];
```

以下是一些常用操作，与 Python 非常相似：

*   索引：`array[2]`
*   赋值：`array[2] = 0`
*   长度：`array.length`
*   在末尾添加元素：`array.push(5)`
*   删除末尾元素：`array.pop()`

你可以在 Mozilla Developer Network（MDN）文档中查看 `Array` 的所有操作；用搜索引擎查找 [“mdn array”](https://www.google.com/search?q=mdn+array) 即可。熟悉 MDN 文档，它会是你的好帮手。

以下是使用数组实现的冰雹序列代码：

```ts
let array: Array<number> = [];
let n: number = 3;
while (n !== 1) {
    array.push(n);
    if (n % 2 === 0) {
        n = n / 2;
    } else {
        n = 3 * n + 1;
    }
}
array.push(n);
```

> **背景扩展：** 与 Python 列表相比，TypeScript 数组要求元素类型一致，例如 `number[]` 只能存放数字，这能在编译阶段发现类型混用问题。

迭代
------------------------------------------------------------------------------------

`for` 循环可以遍历数组元素，就像 Python 一样，只是语法略有不同。例如：

```ts
// find the maximum point of a hailstone sequence stored in array
let max: number = 0;
for (let x of array) {
    max = Math.max(x, max);
}
```

小心！在 Python 中使用 `for ... in ...`，而在 TypeScript 中对应的是 `for ... of ...`。TypeScript 也有 `for...in`，但它遍历的是集合的键（key），而非值。对于数组，键是索引。注意一个单词的差别：

```ts
for (let x in ["a", "b", "c"]) {
    console.log(x);
}
// prints 0, 1, 2
``````ts
for (let x of ["a", "b", "c"]) {
    console.log(x);
}
// prints "a", "b", "c"
```

**遍历数组时，几乎总是使用 `for...of`**，你需要改掉 Python 的习惯。

上面的例子还使用了 `Math.max()`，这是 JavaScript 库中的实用函数。`Math` 类里有很多类似的有用函数——用搜索引擎查找 [“mdn math”](https://www.google.com/search?q=mdn+math) 即可在 MDN 上找到它的文档。

函数
------------------------------------------------------------------------------------

如果想把这段代码封装成可复用模块，我们可以写一个函数：

```ts
/**
 * Compute a hailstone sequence.
 * @param n  starting number for sequence.  Assumes n > 0.
 * @returns hailstone sequence starting with n and ending with 1.
 */
function hailstoneSequence(n: number): Array<number> {
    let array: Array<number> = [];
    while (n !== 1) {
        array.push(n);
        if (n % 2 === 0) {
            n = n / 2;
        } else {
            n = 3 * n + 1;
        }
    }
    array.push(n);
    return array;
}
```

注意函数前的 `/** ... */` 注释，它非常重要。这条注释是函数的**规约（specification）**，描述了操作的输入与输出。规约应简洁、清晰、精确。它提供的信息无法从函数类型中直接看出。比如，它不会说返回值是数字数组，因为 `Array<number>` 的返回类型已经说明了这一点；但它会指出序列以 `n` 开头、以 1 结束，这对调用者至关重要，而类型声明无法表达。

后续课程我们会深入讲解如何撰写优秀的规约，但你得从现在开始阅读并使用它们。

> **学习批注：** 把规约当作“合同”：调用者只需阅读注释即可正确使用函数，无需查看内部实现。良好的规约能显著降低团队协作成本。

值的修改 vs. 变量的重新赋值
---------------------------------------------------------------------------------------------------------------------------------------------------

变化是万恶之源。但优秀的程序员会尽量避免变化，因为变化可能出乎意料。**不可变性（immutability）**——在运行时禁止某些数据被修改——将是本课程的重要设计原则。

例如，**不可变（immutable）**类型指一旦创建其值就永不可变。字符串类型在 Python 和 TypeScript 中都是不可变的。

TypeScript 还允许我们声明不可变引用：即只能赋值一次的变量。要使引用不可重新赋值，用关键字 `const` 而非 `let` 声明：

```ts
const n: number = 5;
```

如果 TypeScript 编译器无法确信你的 `const` 变量在运行时只会被赋值一次，它就会报编译错误。因此，`const` 为“不可重新赋值的引用”提供了静态检查。

尽可能使用 `const` 是良好实践。与变量类型一样，这些声明既是给读者的重要文档，也能被编译器静态检查。#### 阅读练习

记录假设
----------------------------------------------------------------------------------------------------------------

写下变量的类型就是在记录一个假设：例如，变量 `n` 始终指向一个数字。TypeScript 会在编译时检查这一假设，并保证程序中没有任何地方违反它。

将变量声明为 `const` 同样是一种文档形式，声称该变量在初始赋值后永远不会被重新赋值。TypeScript 也会静态地检查这一点。

我们还记录了另一个假设，遗憾的是 TypeScript 不会自动检查：`n` 必须为正数。

为什么要把假设写下来？因为编程充满了假设，如果我们不写下来，就会忘记它们，而将来需要阅读或修改程序的人也无从得知。他们只能猜。

编写程序时必须牢记两个目标：

*   与计算机沟通。首先要说服编译器你的程序是合理的——语法正确且类型正确。然后确保逻辑正确，使其在运行时给出正确结果。
*   与人沟通。让程序易于理解，以便将来有人需要修复、改进或适配时，能够轻松完成。

> **学习批注：** 把假设写成类型或 `const` 声明，相当于给未来维护者留下“防坑指南”。例如，把 `n` 声明为 `const` 就告诉后人“别改它”，减少误操作。

黑客做法 vs. 工程实践
---------------------------------------------------------------------------------------------------------------

我们在本节中写了一些“黑客”代码。黑客做法常常伴随着无节制的乐观：

*   不好：在未测试的情况下写大量代码。
*   不好：把所有细节记在脑子里，假设自己会永远记得，而不是写在代码里。
*   不好：假设 bug 不存在，或者即便存在也很容易找到并修复。

但软件工程不是黑客行为。工程师是悲观主义者：

*   好：一次写一点，边写边测。后续课程会提到测试先行编程（test-first programming）。
*   好：记录代码所依赖的假设。
*   好：让代码能“防蠢”——尤其是防自己！静态检查（static checking）正是为此而生。

> **背景扩展：** “防蠢”原则在工业界叫“防御式编程（defensive programming）”。例如，把函数参数设为只读（`readonly`）或启用严格编译选项，都能在早期把潜在错误拦在门外。

6.031 课程目标
---------------------------------------------------------------------------------------------------

本课程的首要目标是学会如何编写具备以下三大特性的软件：

*   **远离 bug（Safe from bugs）**。正确性（当下行为正确）与防御性（未来行为依旧正确）是我们构建任何软件时必须满足的。
*   **易于理解（Easy to understand）**。代码必须能向未来的维护者清晰地传达意图，后者需要理解并修改它（修复 bug 或新增功能）。那位未来的维护者可能就是几个月甚至几年后的你自己。你会惊讶于自己会忘记多少细节，因此写下来大有裨益；良好的设计也能帮助未来的你。
*   **便于变更（Ready for change）**。软件总是在变。有些设计让修改变得轻而易举，有些则需要大量重写。 

当然，软件还有其他重要属性（如性能、可用性、安全性），它们可能与上述三者存在权衡。但这“三大”是 6.031 最关注的核心，也是软件开发者在实践中普遍放在首位的目标。在学习本课程的每个语言特性、编程实践、设计模式时，都值得思考它们与这三大目标之间的关系。

> **学习批注：**  
> 把“三大目标”贴在桌前：每写一段代码、做一个设计决策，先问自己“这样写更远离 bug 吗？更易读吗？更易改吗？”——长期坚持，工程素养自然提升。

### 为何本课程使用 TypeScript

既然你已经学过 6.009，我们默认你熟悉 Python。那为何本课程不用 Python，而在 6.031 里选择 TypeScript/JavaScript？

**安全性（Safety）** 是首要原因。TypeScript 具备**静态检查（static checking）**，主要是**静态类型（static typing）**，也包括其他编译期检查，例如确保方法确实返回了声明的返回值。本课程研究软件工程，而“远离 bug”是其核心原则之一。TypeScript 把安全性提到很高水平，便于我们学习良好的软件工程实践。当然，用 Python 或 JavaScript 这类动态语言也能写出安全代码，但在一门自带静态检查的安全语言里学习，更容易理解该怎么做。

> **学习批注：** 静态检查就像拼写检查器：写完立刻标红，而不是等到运行时才崩溃。

**普适性（Ubiquity）** 是第二个原因。TypeScript 会编译成纯 JavaScript，而 JavaScript 在研究、教育和工业界无处不在。它不仅运行于浏览器，也用于服务器（Node.js）甚至 Windows/Mac/Linux 桌面应用。

与 Java 相比，TypeScript 的类型系统更丰富，写程序所需的样板代码更少，也更适合开发现代用户界面与 Web 应用。

无论如何，优秀程序员必须**多语言（multilingual）**。编程语言只是工具，必须对症下药。在 MIT 毕业前，你几乎肯定还要再学其他语言（如 Java、C/C++、Scheme、Ruby 或 Haskell），所以现在就开始掌握第二门。

由于 JavaScript 的普适性，它拥有大量有趣且实用的**库（libraries）**，以及优秀的免费**开发工具**（IDE 如 VS Code、编辑器、编译器、测试框架、性能分析器、代码覆盖率、风格检查器）。JavaScript 与 Python 在生态系统丰富度上旗鼓相当，而 TypeScript 能无缝使用所有 JavaScript 库。

使用 JavaScript 也有遗憾之处。它体量庞大，自诞生以来积累了大量特性；还背负 C/C++ 的历史包袱——例如 [`switch` 语句](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Statements/switch) 就是从 C 继承来的过时且不安全的构造。JavaScript 本身起步时也有一些糟糕设计，比如类型转换规则让 [`0 == ""` 返回 true](https://web.mit.edu/6.031/www/sp22/classes/01-static-checking#triple-equals)，[`[] + []` 竟得到空字符串](https://www.destroyallsoftware.com/talks/wat)，以及[比其他语言更少的动态检查](https://web.mit.edu/6.031/www/sp22/classes/01-static-checking#no-checking-in-JS)。TypeScript 修复了 JavaScript 的部分缺陷，但非全部；许多语法现已被废弃，程序员会主动回避，因为它们风险高。

总体而言，TypeScript 目前是学习“远离 bug、易于理解、便于修改”代码的合理选择，而这正是我们的目标。

别误会：本课程的真正技能并不局限于某一门语言，而是可迁移到任何编程语言。课程最重要的收获会超越语言潮流：安全性、清晰性、抽象力与工程直觉。

Summary
--------------------------------------------------------------------------------

今天介绍的核心理念是**静态检查（static checking）**。它与课程目标的关系如下：

*   **远离 bug。** 静态检查在运行前捕获类型错误及其他 bug，提升安全性。

*   **易于理解。** 类型在代码中显式声明，帮助阅读者快速理解。

*   **便于修改。** 静态检查能指出哪些地方需要同步改动，降低重构成本。

> **背景扩展：** 静态检查像建筑图纸审核，施工前发现设计冲突；动态检查像现场监理，施工时发现问题；无检查则像装修完才发现承重墙被敲掉。
