验证 (Validation)
-------------------------------------------------------------------------------

测试是称为_验证 (Validation)_ 的更通用过程的一个示例。验证 (Validation) 的目的是发现程序中的问题，从而增加你对程序正确性的信心。验证 (Validation) 包括：

*   **形式化推理**，通常称为_形式化验证 (Verification)_。形式化验证 (Verification) 构建形式化证明来证明程序是正确的。手动进行形式化验证 (Verification) 很繁琐，自动化工具支持仍是活跃的研究领域。尽管如此，程序中小而关键的部分可以进行形式化验证 (Verification)，例如操作系统中的调度程序，或虚拟机中的字节码解释器，或 [操作系统中的文件系统](http://www.csail.mit.edu/crash_tolerant_data_storage)。
*   **代码审查。** 让其他人仔细阅读你的代码并进行非正式推理，是发现 bug 的好方法。这很像让别人校对你写的文章。我们在 [另一篇阅读材料中讨论代码审查](https://web.mit.edu/6.031/www/sp22/classes/04-code-review/)。
*   **测试**。在精心选择的输入上运行程序并检查结果。

> **背景扩展：** 验证 (Validation) 与形式化验证 (Verification) 常被混淆。简单来说，Verification 是证明“产品是否构建正确”（符合规范），而 Validation 是确认“是否构建了正确的产品”（符合用户需求）。但在本语境下，Validation 是包含 Verification 和 Testing 的广义概念。

即使拥有最好的验证 (Validation)，也很难在软件中实现完美质量。以下是一些典型的_残留缺陷率_（软件发布后留下的 bug）每 kloc（一千行源代码）：

*   1 - 10 defects/kloc：典型行业软件。
*   0.1 - 1 defects/kloc：高质量验证。成熟 Web 浏览器的 JavaScript 库可能达到此正确性水平。
*   0.01 - 0.1 defects/kloc：最好的安全关键验证。NASA 和 Praxis 等公司可以达到此水平。

对于大型系统来说，这可能令人沮丧。例如，如果你发布了一百万行典型的行业源代码（1 defect/kloc），这意味着你遗漏了 1000 个 bug！

> **学习批注：** 接受“残留缺陷”是软件工程现实的一部分。我们的目标不是零 bug（这几乎不可能），而是通过测试将缺陷率降低到可接受的风险水平，尤其是对于安全关键系统。

为何软件测试困难
-------------------------------------------------------------------------------------------------------------------

以下是一些在软件世界中效果不佳的方法。

**穷举测试** 是不可行的。可能测试用例 (Test case) 的空间通常太大，无法穷尽覆盖。想象一下穷举测试一个 32 位浮点乘法运算，`a*b`。这里有 `$2^{64}$` 个测试用例！

> **背景扩展：** `$2^{64}$` 约为 184 亿亿。即使每秒测试 10 亿个用例，也需要数百年才能完成。这说明了为何必须智能地选择测试用例，而非尝试所有输入。

**随意测试**（“试试看是否有效”）不太可能发现 bug，除非程序 bug 太多，以至于任意选择的输入失败的可能性大于成功的可能性。它也不会增加我们对程序正确性的信心。

**随机或统计测试** 对软件效果不佳。其他工程学科可以测试小的随机样本（例如，1% 的制造硬盘）并推断整个生产批次的缺陷率。物理系统可以使用许多技巧来加速时间，比如在 24 小时内打开冰箱 1000 次，而不是 10 年。这些技巧给出了已知的故障率（例如，硬盘的平均寿命），但它们假设缺陷空间具有连续性或均匀性。这对物理制品是正确的。

但软件并非如此。软件行为在可能输入的空间中不连续且离散地变化。系统可能在广泛的输入范围内看起来工作正常，然后在单个边界点突然失败。[著名的 Pentium 除法 bug](http://www.willamette.edu/~mjaneba/pentprob.html) 影响了大约 90 亿次除法中的 1 次。栈溢出、内存不足错误和数值溢出错误往往突然发生，并且总是以相同的方式发生，而不是具有概率变化。这与物理系统不同，物理系统通常有可见证据表明系统正在接近故障点（桥梁中的裂缝），或者故障在故障点附近概率分布（以便统计测试将在到达该点之前观察到一些故障）。

> **学习批注：** 软件 bug 具有“悬崖效应”。物理系统磨损通常是渐进的（如刹车片变薄），而软件可能在输入值从 100 变到 101 时突然崩溃。这就是为何我们需要关注边界值测试。

相反，必须仔细且系统地选择测试用例 (Test case)。系统测试技术是本阅读材料的重点。#### 阅读练习

测试优先编程（Test-first programming）
-------------------------------------------------------------------------------------------------------

在深入之前，我们需要定义一些术语：

*   _模块（Module）_ 是软件系统的一部分，可以独立于系统的其余部分进行设计、实现、测试和推理。在本阅读材料中，我们将关注作为函数的模块。在未来的阅读材料中，我们将拓宽视野，思考更大的模块，比如包含多个交互方法的类。

*   _规范（Specification）_（或 spec）描述了模块的行为。对于函数，规范给出了参数的类型以及对它们的任何额外约束（例如 `sqrt` 的参数必须是非负数）。它还给出了返回值的类型以及返回值如何与输入相关联。在 TypeScript 代码中，规范由函数签名及其上方描述其功能的注释组成。

*   模块有一个提供其行为的 _实现（Implementation）_，以及使用该模块的 _客户端（Clients）_。对于函数，实现是函数体，客户端是调用函数的其他代码。模块的规范约束了客户端和实现。我们将在几节课后更多关于规范、实现和客户端的内容。

*   _测试用例（Test case）_ 是特定的输入选择，以及规范要求的预期输出行为。

*   _测试套件（Test suite）_ 是模块的一组测试用例。

> **学习批注：** 规范是客户端与实现之间的契约。明确规范有助于解耦，使得实现可以在不破坏客户端的前提下进行修改，只要它依然满足规范。

你已经在问题集 0 中开始使用这些概念了。你获得了一些 TypeScript 函数的规范，并被要求为每个函数编写实现。你还获得了每个函数的测试套件，你可以运行它们来查看你的实现是否遵守了规范。

事实证明，这是从头设计程序时要遵循的良好模式。在 _测试优先编程（Test-first programming）_ 中，你在编写任何代码之前先编写规范和测试。单个函数的开发按以下顺序进行：

1.   **规范**：为函数编写规范。
2.   **测试**：编写锻炼规范的测试。
3.   **实现**：编写实现。

一旦你的实现通过了你编写的测试，你就完成了。

系统化测试（Systematic testing）
-----------------------------------------------------------------------------------------------

我们希望进行_系统化_测试，而不是穷举测试（exhaustive testing）、随意测试（haphazard testing）或随机测试（randomized testing）。系统化测试意味着我们以原则性的方式选择测试用例（test case），目标是设计具备三个理想属性的测试套件（test suite）：

*   **正确（Correct）**。一个正确的测试套件是规范（specification）的合法客户端，它能毫无怨言地接受规范的所有合法实现（implementation）。这让我们可以自由地更改模块内部的实现方式，而不必非要更改测试套件。

*   **彻底（Thorough）**。一个彻底的测试套件能发现实现中的实际缺陷（bug），这些缺陷是由程序员可能犯的错误引起的。

*   **小巧（Small）**。一个小巧的测试套件包含少量测试用例，最初编写更快，如果规范演变也更容易更新。小巧的测试套件运行也更快。如果测试套件小巧且快速，你将能够更频繁地运行测试。

> **学习批注：** 为什么测试套件要“小巧”？想象一下，如果每次运行测试都要等 10 分钟，你还会每次保存代码后都运行吗？快速反馈是测试驱动开发的核心，小巧的套件能确保你愿意频繁运行它们，从而尽早发现问题。

根据这些标准，穷举测试虽然彻底但规模大到不可行。随意测试往往小巧但不彻底。随机测试只有以规模庞大为代价才能实现彻底性。

设计一个既彻底又小巧的测试套件需要正确的态度。通常当你编码时，你的目标是让程序运行起来。但作为测试套件设计者，你想要_让它失败_。这是一个微妙但重要的区别。优秀的测试者会故意戳探程序所有可能脆弱的地方，以便消除这些脆弱点。

> **背景扩展：** 这种“破坏者”心态与开发者心态截然不同。开发者想构建功能，测试者想寻找裂缝。测试优先编程强迫你在写代码前先思考“怎么弄坏它”，从而写出更健壮的代码。就像建筑师不仅要设计大楼，还要模拟地震来测试结构强度一样。

需要采用测试态度是支持测试优先编程（Test-first programming）的另一个理由。人们很容易禁不住诱惑，将自己已编写的代码视为珍贵之物、脆弱的蛋壳，仅为了看它运行而进行非常轻微的测试。然而，为了进行_彻底_的测试，你必须得严苛一点。测试优先编程允许你在编写任何代码之前就戴上测试帽，采纳那种严苛的视角。#### 阅读练习

通过划分（Partitioning）选择测试用例
---------------------------------------------------------------------------------------------------------------------------------

创建一个好的测试套件是一个具有挑战性且有趣的设计问题。我们想挑选一组测试用例，既要小到易于编写、维护和快速运行，又要足够完备以发现程序中的 bug。

![图 2：函数输入空间的划分](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/partition.png)

为此，我们将输入空间划分为_子域（Subdomain）_，每个子域由一组输入组成。（名称_子域_源于它是数学函数输入空间_域_的子集这一事实。）合在一起，这些子域形成一个_划分（Partitioning）_：一组不相交的集合，完全覆盖输入空间，使得每个输入恰好位于一个子域中。然后我们从每个子域中选择一个测试用例，这就是我们的测试套件。

子域背后的思想是将输入空间划分为程序行为相似的输入集。然后我们使用每个集合的一个代表。这种方法通过选择不同的测试用例，充分利用有限的测试资源，迫使测试探索随机测试可能无法触及的输入空间区域。

> **背景扩展：** 想象测试一个绝对值函数 `abs(x)`。输入空间是所有整数。我们可以划分为三个子域：负数、零、正数。在这三个子域中，程序行为逻辑相似（负数取反，零不变，正数不变）。只需从每个子域选一个代表（如 -5, 0, 5），就能高效覆盖主要逻辑路径，而无需测试所有整数。
#### 示例：`abs()`

让我们从 JavaScript 库中的一个简单示例开始，即 [`Math.abs()`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/abs) 函数：

```ts
/**
 * ...
 * @param a  the argument whose absolute value is to be determined
 * @returns the absolute value of the argument.
 */
function abs(a: number): number
```


从数学角度来看，这是一个具有以下类型的函数：

**abs : number → number**

![Image 3: partitioning-abs](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/abs-partition.png)

该函数拥有一个一维输入空间（input space），由 _a_ 的所有可能值组成。考虑到绝对值函数的行为方式，我们可以开始将输入空间**划分（Partitioning）**为以下两个**子域（Subdomain）**：{ _a_ | _a_ ≥ 0 } 和 { _a_ | _a_< 0 }。在第一个子域上，`abs` 应返回不变的 _a_。在第二个子域上，`abs` 应将其取反。

> **学习批注：** 划分（Partitioning）的核心思想是将无限或庞大的输入空间划分为有限个行为相似的子域。这样我们只需从每个子域中选取少量代表样本，而非测试所有可能的输入。例如，对于所有正数，程序行为一致，因此测试其中一个正数（如 17）通常足以代表该子域。

为了紧凑地编写划分，我们省略每个集合描述中的 { _a_ | … } 框架，只需如下所示编写谓词列表：

```ts
// partition: a >= 0; a < 0
```


为了为我们的**测试套件（Test suite）**选择**测试用例（Test case）**，我们从划分的每个子域中选取一个任意值 _a_，例如：

*   _a_ = 17 以覆盖子域 _a_ ≥ 0
*   _a_ = -3 以覆盖子域 _a_< 0

> **背景扩展：** 这里选取的是子域内部的典型值。在实际测试中，我们还需特别关注子域的“边界（Boundary）”，例如 0 本身，因为 off-by-one 等错误常发生在边界条件上。
#### 示例：`max()`

现在让我们看看 JavaScript 库中的另一个示例，[`Math.max()`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Math/max)。尽管 `max()` 可以接受任意数量的参数，但我们现在只关注双参数形式：

```ts
/**
 * ...
 * @param a  an argument
 * @param b  another argument
 * @returns the larger of a and b.
 */
function max(a: number, b: number): number
```

从数学角度来看，这是一个双参数函数：

**max : number × number → number**

![Image 4: partitioning-max](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/max-partition.png)

因此，我们有一个二维输入空间（Input space），由所有整数对 (_a_,_b_) 组成。现在让我们对其进行划分（Partitioning）。根据规范（Specification），选择子域（Subdomain）{ (_a_,_b_) | _a_<_b_ } 和 { (_a_,_b_) | _a_>_b_ } 是合理的，因为规范要求在每种情况下有不同的行为：前一个子域中的输入应返回 _b_，而后一个子域中的输入应返回 _a_。

> **学习批注：** 划分（Partitioning）的核心在于“不重不漏”。这里特别强调了 `_a_ = _b_` 的情况，因为在编程中边界（Boundary）最容易被忽略。就像检查门禁系统时，不仅要测试“身高高于 1 米”和“低于 1 米”，还必须测试“正好 1 米”的情况。

但我们不能就此止步，因为这些子域尚未构成输入空间的_划分_。划分必须完全覆盖所有可能的输入集合。因此我们需要添加 { (_a_,_b_) | _a_ = _b_ }，此时函数可以返回 _a_ 或 _b_。简洁地表达，划分看起来是这样的：

```ts
// partition: a < b; a > b; a = b
```

我们的测试套件（Test suite）可能是：

*   (_a_,_b_) = (1, 2) 覆盖 _a_<_b_
*   (_a_,_b_) = (10, -8) 覆盖 _a_>_b_
*   (_a_,_b_) = (9, 9) 覆盖 _a_ = _b_

> **学习批注：** 测试套件不需要包含子域中的所有值，只需从每个子域中选取一个代表性测试用例（Test case）即可。例如选 (1, 2) 代表所有 _a_<_b_ 的情况，这大大减少了测试工作量。

查看解释### 在划分（Partitioning）中包含边界（Boundary）

缺陷（bug）经常出现在子域（Subdomain）之间的_边界（Boundary）_处。一些示例如下：

*   0 是正数和负数之间的边界
*   数值类型的最大值和最小值，如 [`Number.MAX_SAFE_INTEGER`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_SAFE_INTEGER) 或 [`Number.MAX_VALUE`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Number/MAX_VALUE)
*   集合类型的空值，如空字符串、空数组或空集
*   序列的第一个和最后一个元素，如字符串或数组

为什么缺陷经常发生在边界处？其中一个原因是程序员经常犯**差一错误（off-by-one mistakes）**，例如编写 `<=` 而不是 `<`，或者将计数器初始化为 0 而不是 1。另一个原因是某些边界可能需要在代码中作为特殊情况处理。还有一个原因是边界可能是代码行为不连续的地方。例如，当用作整数的 `number` 变量增长超过 `Number.MAX_SAFE_INTEGER` 时，它会突然开始失去精度。

> **学习批注：** 差一错误是新手最常遇到的陷阱之一。想象一下爬楼梯：如果你站在第 1 级台阶，再走 1 步是第 2 级；但如果你从地面（第 0 级）开始数，走 1 步才是第 1 级。循环中的 `<` 与 `<=` 混淆往往就源于这种起始点的认知差异。

我们将边界作为单元素子域纳入划分中，以便测试套件（Test suite）必然包含该边界值作为测试用例（Test case）。对于 `abs`，我们将为相关边界添加一个子域：

*   _a_ = 0，因为 `abs` 在正数和负数上的表现不同

我们原来的两个子域将缩小以排除边界值：{ _a_ | _a_> 0 } 和 { _a_ | _a_< 0 }。

> **背景扩展：** 将边界单独划分为一个子域，确保了测试一定会覆盖这些高风险点。这就像过安检时，不仅检查普通行李，还要专门检查可疑物品，虽然增加了步骤，但显著降低了漏检风险。

这仍然是 `abs` 输入空间的一个划分：三个子域不相交且完全覆盖该空间。一种紧凑的写法如下：

```ts
// partition:
//     a < 0
//     a = 0
//     a > 0
```

我们的测试套件随后可能是：

*   _a_ = 0
*   _a_ = 17 以覆盖子域 _a_> 0
*   _a_ = -3 以覆盖子域 _a_< 0

让我们来看一个稍微复杂一点的例子。[`BigInt`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/BigInt) 是 TypeScript 内置的一种类型，它可以表示任意大小的整数，不像类型 `number` 只有有限的范围。`BigInt` 支持常规的整数运算，如 `+`、`-`、`*`、`/` 和 `**`。例如，以下是它的使用方式：

```ts
let a = BigInt(Number.MAX_SAFE_INTEGER); // 2^53 - 1
let b = BigInt(2);
let ab = a * b; // should be 2^54 - 2
```


我们可以将 `*` 视为一个（重载）函数，它接受两个输入，每个输入的类型均为 `BigInt`，并产生一个类型为 `BigInt` 的输出：

**multiply : BigInt × BigInt → BigInt**

我们同样有一个二维输入空间，由所有整数对 (_a_,_b_) 组成。考虑到符号规则在乘法中的工作方式，我们可能会从这些 `子域（Subdomain）` 开始：

*   _a_ 和 _b_ 均为正数
*   _a_ 和 _b_ 均为负数
*   _a_ 为正数，_b_ 为负数
*   _a_ 为负数，_b_ 为正数

> **学习批注：** 为什么要按符号划分子域？因为符号组合直接决定了结果的行为（例如正负性）。这就好比分类讨论数学题，不同符号组合下的逻辑路径不同，因此需要分别测试以确保每种逻辑分支都正确。

还有一些我们需要检查的 `边界（Boundary）` 值：

*   _a_ 或 _b_ 为 0，因为结果始终为 0
*   _a_ 或 _b_ 为 1，这是乘法的单位元

最后，因为 `BigInteger` 的目的是表示任意大的整数，我们应该确保尝试非常大的整数，至少要比 `Number.MAX_SAFE_INTEGER` 大，即 2 53-1，一个 16 位的十进制整数。

*   _a_ 或 _b_ 的幅度较小或较大（即小到可以在 `number` 值中精确表示，或大到超出 `number` 的范围）

让我们将所有这些观察结果整合到一个完整的 `划分（Partitioning）` 中，覆盖整个 (_a_,_b_) 空间。我们将独立地从以下选项中选择 _a_ 和 _b_：

![图 5：multiply() 的划分](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/multiply-partition.png)

*   0
*   1
*   小正整数（≤ `Number.MAX_SAFE_INTEGER` 且 > 1）
*   小负整数（≥ `Number.MIN_SAFE_INTEGER` 且 < 0）
*   大正整数（>`Number.MAX_SAFE_INTEGER`）
*   大负整数（<`Number.MIN_SAFE_INTEGER`）

因此，这将产生 6 × 6 = 36 个 `子域（Subdomain）` 来划分整数对的空间。

为了从这个划分生成 `测试套件（Test suite）`，我们从网格的每个方块中选择一个任意对 (_a_,_b_)，例如：

*   (_a_,_b_) = (0, 0) 覆盖 (0, 0)
*   (_a_,_b_) = (0, 1) 覆盖 (0, 1)
*   (_a_,_b_) = (0, 8392) 覆盖 (0, 小正整数)
*   (_a_,_b_) = (0, -7) 覆盖 (0, 小负整数)
*   …
*   (_a_,_b_) = (-10 60, -10 810) 覆盖 (大负数，大负数)

> **背景扩展：** 这里体现了系统化测试的核心思想：不需要测试所有可能的输入（那是无限的），而是通过划分空间，从每个具有相似行为的区域中选取代表性的 `测试用例（Test case）`。就像品尝一锅汤，不需要喝光整锅，只需搅拌均匀后尝一勺即可判断味道。

右侧的图表展示了二维 (a,b) 空间如何被此划分分割，其中的点是我们可能选择用来完全覆盖该划分的测试用例。### 使用多个划分 (Partitions)

目前的示例仅使用了一个划分 (Partitioning)——即跨越整个输入空间的一组不相交子域 (Subdomain)。对于具有多个参数的函数，这样做成本可能会很高。每个参数都可能有趣的行为变化和多个边界值，因此从每个参数行为的_笛卡尔积 (Cartesian product)_ 形成输入空间的单个划分，会导致 resulting 测试套件 (Test suite) 的大小出现组合爆炸。我们在 `BigInt` 乘法中已经看到了这一点，其中笛卡尔积划分已经有 6 × 6 = 36 个子域，需要 36 个测试用例 (Test case) 来覆盖。对于具有 _n_ 个参数的函数，笛卡尔积方法产生的测试套件大小关于 _n_ 呈指数级增长，这对于手动编写测试来说很快变得不可行。

> **学习批注：** 想象一下你要测试一个表单，它有 5 个输入框，每个框有 10 种可能的状态。如果使用笛卡尔积，你需要测试 10^5 = 100,000 种组合！这就是为什么我们需要更聪明的策略，而不是盲目测试所有组合。

![Image 6: partitioning multiply() with separate a and b partitions](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/multiply-a-b-partition.png)

一种替代方法是将每个输入 _a_ 和 _b_ 的特征视为输入空间的两个独立划分。一个划分仅考虑 _a_ 的值：

*   (_a_,_b_) 使得 _a_ = 0, 1, 小正数，小负数，大正数，大负数

另一个划分仅考虑 _b_ 的值：

*   (_a_,_b_) 使得 _b_ = 0, 1, 小正数，小负数，大正数，大负数

这两个划分如右图所示。每个输入对 (_a_,_b_) 恰好属于每个划分中的一个子域。

> **背景扩展：** 这种策略类似于“正交数组测试”的思想。我们不再测试所有可能的 (a, b) 组合，而是确保每个参数的每种情况都被至少测试一次。这大大减少了工作量，同时仍能捕捉到大部分单一参数引起的错误。

我们可以简洁地写出这两个划分，如下所示：

```ts
// partition on a:
//   a = 0
//   a = 1
//   a is small integer > 1
//   a is small integer < 0
//   a is large positive integer
//   a is large negative integer
//      (where "small" fits in a TypeScript number, and "large" doesn't)
// partition on b:
//   b = 0
//   b = 1
//   b is small integer > 1
//   b is small integer < 0
//   b is large positive integer
//   b is large negative integer
```


我们仍然希望用测试用例覆盖每个子域，但现在单个测试用例可以覆盖来自不同划分的多个子域，从而使测试套件更高效。我们可以仅用 6 个测试用例完全覆盖这两个划分，如右图所示。

![Image 7: partitioning multiply() on the signs of a and b](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/multiply-sign-partition.png)

独立划分 _a_ 和 _b_ 会增加你不再测试它们之间交互的风险。例如，乘法中的符号处理是一个可能的 bug 来源，结果的符号取决于 _a_ 和 _b_ 两者的符号。但我们可以添加一个额外的划分来捕捉这种交互：

```ts
// partition on signs of a and b:
//    a and b are both positive
//    a and b are both negative
//    a positive and b negative
//    a negative and b positive
//    one or both are 0
```


现在我们有三个划分，每个划分分别有 6、6 和 5 个子域，但我们不需要 6 × 6 × 5 个测试用例的笛卡尔积来覆盖它们。一个包含 6 个精心选择的测试用例的测试套件可以覆盖所有三个划分的子域。

我们可以继续以这种方式添加划分，随着我们对规范 (spec) 的思考加深，并观察到其他可能导致 bug 的行为变化。通过精心选择测试用例，额外的划分应该只需要很少（如果有）的额外测试用例。

有时我们可能希望对多个划分使用笛卡尔积方法，以生成更彻底的测试套件。但即使在这些情况下，笛卡尔积也可能比我们预期的要小。当来自不同划分的子域被证明是互斥时，笛卡尔积不会包含该特定子域组合的子域。我们将在下面的练习之一中看到这样的示例。

然而，作为测试优先编程 (Test-first programming) 的起点，一个覆盖几个精心选择的划分的每个子域的小型测试套件，在大小和彻底性之间取得了良好的平衡。随后，测试套件可以通过白盒测试 (Glass box testing)、代码覆盖率 (Coverage) 测量和回归测试 (Regression testing) 进一步增长，我们将在本阅读的后面部分看到这些内容。#### 阅读练习

自动化单元测试（Unit test）
-------------------------------------------------------------------------------------------------------

一个经过良好测试的程序将为其包含的每个独立模块都设有测试。尽可能隔离地测试单个模块的测试称为 **单元测试（Unit test）**。

大多数编程语言至少有一个流行的库用于编写自动化单元测试，包括 Java 的 [JUnit](http://junit.org/junit5/) 和 Python 的 [unittest](https://docs.python.org/3/library/unittest.html)。对于 JavaScript 和 TypeScript，一个流行的选择是 [Mocha](https://mochajs.org/)。

Mocha 单元测试编写为对函数 `it()` 的调用，第一个参数是测试名称，第二个参数是测试主体（编写为函数表达式）。测试主体通常包含对被测模块的一个或多个调用，然后使用断言函数检查结果，如 [`assert`](https://nodejs.org/dist/latest-v16.x/docs/api/assert.html#assertvalue-message)、[`assert.strictEqual`](https://nodejs.org/dist/latest-v16.x/docs/api/assert.html#assertstrictequalactual-expected-message) 或 [`assert.throws`](https://nodejs.org/dist/latest-v16.x/docs/api/assert.html#assertthrowsfn-error-message)。例如，`max` 的单个单元测试可能如下所示：

```ts
it("covers a < b", function() {
  assert.strictEqual(Math.max(1, 2), 2);
});
```


注意 `assert.strictEqual` 参数的顺序很重要。第一个参数应该是_实际_结果，即代码实际执行的结果。第二个参数应该是_预期_结果，通常是常量，即测试希望看到的结果。如果你把它们颠倒了，当测试失败时，Mocha 可能会产生令人困惑的错误消息。断言还可以接受一个可选的消息字符串作为最后一个参数，你可以用它使测试失败信息更清晰。

要将一组单元测试收集到测试套件（Test suite）中，请将它们放在对 `describe()` 的调用内。例如，上面我们为 `max` 选择的测试在 Mocha 中实现时可能如下所示：

```ts
describe("Math.max", function() {
  it("covers a < b", function() {
    assert.strictEqual(Math.max(1, 2), 2);
  });

  it("covers a = b", function() {
    assert.strictEqual(Math.max(9, 9), 9);
  });

  it("covers a > b", function() {
    assert.strictEqual(Math.max(10, -9), 10);
  });
});
```


测试套件可以包含任意数量的 `it()` 函数，当你使用 Mocha 运行测试套件时，它们会独立运行。如果测试用例中的断言失败，则该测试用例立即返回，Mocha 会记录该测试失败。即使一个测试失败，套件中的其他测试仍将继续运行。

> **学习批注：** 单元测试的核心在于“隔离”。如果一个测试失败了，它应该能明确指出是哪个模块的问题，而不是因为依赖的其他模块出错。Mocha 的独立运行机制确保了单个失败不会阻断后续测试，这有助于快速定位回归错误。

*   对结构的属性使用简单的 ``assert`` 和 ``strictEqual`` 断言。这在最有用时，如在前一个练习中，存在多个正确输出的情况。

黑盒测试（Black box testing）与白盒测试（Glass box testing）
-------------------------------------------------------------------------------------------------------------------------

回顾上文，_规范（specification）_ 是对函数行为的描述——参数类型、返回值类型以及它们之间的约束和关系。

**黑盒测试（Black box testing）** 意味着仅根据规范而非函数的实现来选择测试用例（Test case）。这就是我们目前在示例中所做的。我们在 `abs`、`max` 和 `BigInt` 乘法中进行了划分（Partitioning）并寻找边界（Boundary），而没有查看这些函数的实际代码。事实上，如果我们遵循测试优先编程（Test-first programming）方法，我们甚至还没有为这些函数_编写_代码。

> **学习批注：** 黑盒测试的核心优势在于它与实现细节解耦。想象你在测试一个微波炉：你只关心输入（时间、功率）和输出（热好的食物），而不关心内部磁控管是如何工作的。这样即使内部零件升级，只要加热效果不变，测试依然通过。

**白盒测试（Glass box testing）** 意味着基于函数实际实现的知识来选择测试用例。例如，如果实现根据输入选择不同的算法，那么你应该围绕选择不同算法的点进行划分。如果实现保持一个内部缓存来记住先前输入的答案，那么你应该测试重复的输入。

> **背景扩展：** 白盒测试就像拥有微波炉的电路图。如果你知道微波炉在加热超过 5 分钟时会切换散热风扇，你就需要专门测试 4 分钟和 6 分钟的情况，以确保风扇切换逻辑正确。这能发现黑盒测试容易遗漏的内部逻辑错误。

对于 `BigInt` 乘法的情况，当我们最终实现它时，我们可能决定将整数表示为十进制数字数组。这个决定在函数行为中引入了新的边界。乘以两个单位数字是微不足道的，但两个或更多数字的数组需要多位数乘法的更大复杂性。因此，这种实现的白盒测试可能会基于内部数组的长度引入新的划分。（对于 `BigInt` 更有效的表示可能是像 [`Uint32Array`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Uint32Array) 这样的 32 位无整数数组，但原则是相同的——基数为 2^32 而不是基数为 10 的数字序列。）

在进行白盒测试时，你必须注意你的测试用例不要_要求_特定的实现行为，除非规范中明确调用了该行为。例如，如果规范说“如果输入格式不佳则抛出异常”，那么你的测试不应该_专门_检查 `TypeError` 异常，仅仅因为这是当前实现所做的。此时的规范允许抛出_任何_异常，因此你的测试用例也应该是通用的以便正确，并保留实现者的自由。我们将在关于规范的课程中对此多说一些。

> **学习批注：** 过度依赖实现细节会导致测试脆弱。如果你测试了“必须抛出 ValueError"，而后来开发者优化代码改抛了"FormatError"（同样符合规范），你的测试就会失败，即使代码功能正常。测试应验证“是否抛出异常”，而非“抛出哪个具体异常”。

覆盖率（Coverage）
---------------------------------------------------------------------------

评估测试套件（Test suite）的一种方法是询问它在多大程度上彻底锻炼了程序。这个概念称为_覆盖率（Coverage）_。以下是三种常见的覆盖率类型：

*   **语句覆盖率（Statement coverage）**：是否有某个测试用例运行了每条语句？
*   **分支覆盖率（Branch coverage）**：对于程序中的每个 `if` 或 `while` 语句，是否有某个测试用例同时采取了真（true）和假（false）两个方向？
*   **路径覆盖率（Path coverage）**：是否有某个测试用例采取了所有可能的分支组合——即穿过程序的每条路径？

[![图 8：Istanbul 代码覆盖率工具的输出示例](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/istanbul.png)](https://web.mit.edu/6.031/www/sp22/classes/03-testing/figures/nyc.png)

> **学习批注：** 覆盖率强度依次递增：语句 < 分支 < 路径。想象一个包含循环的程序，路径数量可能是无限的（例如循环 1 次、2 次...n 次），因此追求 100% 路径覆盖率通常是不现实的，而 100% 语句覆盖率则是业界常见的基础目标。

分支覆盖率比语句覆盖率更强（需要更多测试才能达到），路径覆盖率比分支覆盖率更强。在业界，100% 语句覆盖率是一个常见目标，但由于存在无法到达的防御性代码（如“绝不应到达此处”的断言），即使这一点也很少实现。100% 分支覆盖率是非常理想的，安全关键型行业代码甚至有更苛刻的标准（例如 [MC/DC](https://en.wikipedia.org/wiki/Modified_condition/decision_coverage)，修改条件/决策覆盖率）。不幸的是，100% 路径覆盖率是不可行的，需要指数级大小的测试套件才能实现。

一种标准的测试方法是添加测试，直到测试套件达到足够的语句覆盖率：即程序中的每个可到达语句都至少被一个测试用例执行。在实践中，语句覆盖率通常由代码覆盖率工具测量，该工具计算测试套件运行每个语句的次数。使用此类工具，白盒测试很容易；你只需测量黑盒测试的覆盖率，并添加更多测试用例，直到所有重要语句都被记录为已执行。

JavaScript 和 TypeScript 的一个良好代码覆盖率工具是 [Istanbul/nyc](https://istanbul.js.org/)，如右图所示。在工具的 HTML 输出中，已被测试套件执行的行在左边距有一个绿色标记（同时也显示该行被执行的次数）。尚未覆盖的行显示为红色。包含仅在一个方向执行的分支的行——始终为真但从不为假，或反之——有一个 I 或 E 图标，指示哪条路径从未被采用（I 代表"if"，E 代表"else"）。如果你从覆盖率工具中看到右侧的结果，你的下一步将是想出一个测试用例，使 `if` 测试至少有一次为真，并将其添加到测试套件中，以便红线变为绿线。

> **背景扩展：** 这种“红变绿”的过程是测试驱动开发的核心反馈循环。红色代表未覆盖或有缺陷的区域，绿色代表已通过验证。通过持续监控覆盖率报告，开发者可以直观地看到测试盲区，从而有针对性地补充测试用例，而不是盲目编写测试。

单元测试 (Unit test) 与集成测试 (Integration test)
-------------------------------------------------------------------------------------------------------------------

到目前为止，我们一直在讨论**单元测试 (Unit test)**，即隔离测试单个模块 (Module) 的测试。隔离测试模块 (Module) 会使调试变得容易得多。当模块 (Module) 的单元测试 (Unit test) 失败时，你可以更有信心地认为缺陷 (bug) 存在于该模块 (Module) 中，而不是程序的任何其他地方。

> **背景扩展：** 想象一下你在修理一辆车。单元测试就像单独测试发动机、刹车或轮胎。如果刹车测试失败，你知道问题就在刹车系统。而集成测试则是把车组装好后开一圈，如果车跑偏了，可能是轮胎、悬挂或转向系统的问题，排查范围更大。

与单元测试 (Unit test) 相反，**集成测试 (Integration test)** 测试模块 (Module) 的组合，甚至是整个程序。如果你只有集成测试 (Integration test)，那么当测试失败时，你必须搜寻缺陷 (bug)。它可能在程序的任何地方。集成测试 (Integration test) 仍然很重要，因为程序可能在模块 (Module) 之间的连接处失败。例如，一个模块 (Module) 可能期望的输入与它实际上从另一个模块 (Module) 获得的输入不同。但是，如果你有一套彻底的单元测试 (Unit test) 让你对单个模块 (Module) 的正确性有信心，那么你在寻找缺陷 (bug) 时需要搜索的范围就会小得多。

假设你正在构建一个文档搜索引擎。你的两个模块 (Module) 可能是 `load()`（加载文件）和 `extract()`（将文档拆分为其组成单词）：

```ts
/** 
 * @returns the contents of the file
 */
function load(filename: string): string { ... }

/** 
 * @returns the words in string s, in the order they appear, 
 *         where a word is a contiguous sequence of 
 *         non-whitespace and non-punctuation characters 
 */
function extract(s: string): Array<string> { ... }
```

这些函数可能被另一个模块 (Module) `index()` 用来制作搜索引擎的索引：

```ts
/**
 * @returns an index mapping a word to the set of filenames
 *         containing that word, for all files in the input set 
 */
function index(filenames: Set<string>): Map<string, Set<string>> {
    ...
    for (let file of files) {
        let doc = load(file);
        let words = extract(doc);
        ...
    }
    ...
}
```

在我们的测试套件 (Test suite) 中，我们将需要：

*   仅针对 `load` 的单元测试 (Unit test)，在各种文件上测试它
*   仅针对 `extract` 的单元测试 (Unit test)，在各种字符串上测试它
*   针对 `index` 的单元测试 (Unit test)，在各种文件集上测试它

程序员有时犯的一个错误是以这样一种方式编写 `extract` 的测试用例 (Test case)：测试用例 (Test case) 依赖于 `load` 是正确的。例如，测试用例 (Test case) 可能使用 `load` 加载文件，然后将其结果作为输入传递给 `extract`。但这_不是_ `extract` 的单元测试 (Unit test)。如果测试用例 (Test case) 失败，那么我们不知道失败是由于 `load` 中的缺陷 (bug) 还是 `extract` 中的缺陷 (bug)。

最好孤立地思考和测试 `extract`。使用涉及真实文件内容的测试划分 (Partitioning) 可能是合理的，因为这就是 `extract` 在程序中的实际使用方式。但不要实际上从测试用例 (Test case) 调用 `load`，因为 `load` 可能有缺陷 (bug)！相反，将文件内容存储为字面字符串，并直接传递给 `extract`。这样你就是在编写孤立的单元测试 (Unit test)，如果它失败，你可以更有信心地认为缺陷 (bug) 在于它实际测试的模块 (Module) 中。

请注意，`index` 的单元测试 (Unit test) 不能轻易地以这种方式孤立。当测试用例 (Test case) 调用 `index` 时，它不仅测试 `index` 内部的代码正确性，还测试 `index` 调用的所有函数。如果测试失败，缺陷 (bug) 可能在于这些函数中的任何一个。这就是为什么我们希望为 `load` 和 `extract` 编写单独的测试，以增加我们对这些模块 (Module) 个体的信心，并将问题局限在连接它们的 `index` 代码上。

如果我们编写它所调用模块 (Module) 的**桩 (Stub)** 版本，孤立像 `index` 这样的高级模块 (Module) 是可能的。例如，`load` 的桩 (Stub) 根本不会访问文件系统，而是无论传递给它什么 `File`，都会返回模拟文件内容。类的桩 (Stub) 通常被称为 [**模拟对象 (Mock object)**](http://en.wikipedia.org/wiki/Mock_object)。桩 (Stub) 是构建大型系统时的重要技术，但我们在 6.031 中通常不使用它们。#### 阅读练习

自动化回归测试（Automated Regression Testing）
-------------------------------------------------------------------------------------------------------------------

没有什么比完全自动化更能让测试变得易于运行且更可能被执行了。**自动化测试（Automated Testing）** 意味着自动运行测试并检查结果。

运行模块测试的代码称为_测试驱动程序（test driver）_（也称为测试 harness 或测试 runner）。测试驱动程序不应是一个交互式程序，提示你输入并打印结果供你手动检查。相反，测试驱动程序应在固定测试用例（Test Case）上调用模块本身，并自动检查结果是否正确。测试驱动程序的结果应该是“所有测试通过”或“这些测试失败：…"。一个好的测试框架（如 Mocha）允许你构建和运行这种测试驱动程序，以及一套自动化测试用例。

请注意，像 Mocha 这样的自动化测试框架让运行测试变得容易，但你仍然必须自己想出好的测试用例（Test Case）。_自动测试生成_ 是一个难题，仍然是计算机科学研究的活跃主题。

一旦拥有了测试自动化，当你修改代码时重新运行测试就非常重要。软件工程师从痛苦的经验中得知，对大型或复杂程序的_任何_更改都是危险的。无论你是在修复另一个 bug、添加新功能，还是优化代码以提高速度，一个能保留正确行为基线的自动化测试套件（Test Suite）——即使只有几个测试——也能挽救你的项目。在更改代码时频繁运行测试可以防止程序_回归（regressing）_ — 即在修复新 bug 或添加新功能时引入其他 bug。每次更改后运行所有测试称为**回归测试（Regression Testing）**。

> **背景扩展：** “回归”一词意味着退步或回到旧状态。在软件中，回归缺陷（Regression Bug）指的是原本已修复的功能在新版本中再次失效。例如，如果你修复了登录页面的密码错误，但下次更新后密码验证又坏了，这就是回归。

每当你发现并修复一个 bug 时，将引发该 bug 的输入作为测试用例（Test Case）添加到自动化测试套件（Test Suite）中。这种测试用例称为_回归测试（Regression Test）_。这有助于用好的测试用例填充你的测试套件（Test Suite）。请记住，如果一个测试能引发 bug，它就是好测试——而每个回归测试（Regression Test）曾在你的某个代码版本中引发过 bug！保存回归测试（Regression Test）还可以防止重新引入该 bug 的倒退行为。这个 bug 可能是一个容易犯的错误，因为它已经发生过一次了。

这个想法也引出了_测试优先调试（test-first debugging）_。当出现 bug 时，立即为其编写一个能引发该 bug 的测试用例（Test Case），并立即将其添加到测试套件（Test Suite）中。一旦你找到并修复了 bug，你所有的测试用例（Test Case）都将通过，你就完成了调试，并且为该 bug 拥有了一个回归测试（Regression Test）。

在实践中，这两个想法，自动化测试和回归测试（Regression Testing），几乎总是结合使用。只有当测试可以频繁自动运行时，回归测试（Regression Testing）才切实可行。相反，如果你已经在项目中实施了自动化测试，那么不妨用它来防止回归。所以**自动化回归测试（Automated Regression Testing）** 是现代软件工程的最佳实践。#### 阅读练习

迭代式测试优先编程（Iterative test-first programming）
---------------------------------------------------------------------------------------------------------------------------

让我们重温本章开始时介绍的测试优先编程（Test-first programming）理念，并加以完善。有效的软件工程并非遵循线性过程。请实践**迭代式**测试优先编程（Test-first programming），即准备好回到之前的步骤并修改工作：

1.   编写函数的规范（Specification）。
2.   编写测试以锻炼规范（Specification）。发现问题时，**迭代**规范（Specification）和测试。
3.   编写实现（Implementation）。发现问题时，**迭代**规范（Specification）、测试和实现（Implementation）。

每个步骤都有助于验证（Validation）之前的步骤。编写测试是理解规范（Specification）的好方法。规范（Specification）可能不正确、不完整、含糊不清或缺少边界情况。尝试编写测试可以尽早发现这些问题，避免浪费时间在基于有缺陷规范（Specification）的实现（Implementation）上。同样，编写实现（Implementation）可能帮助你发现缺失或不正确的测试，或促使你重新审视并修改规范（Specification）。

> **学习批注：** 这里的“验证（Validation）”指的是确认我们是否在构建正确的产品（符合需求），而不仅仅是构建产品的方式是否正确。测试作为中间产物，起到了连接规范与实现的桥梁作用。

由于可能需要迭代之前的步骤，因此在进入下一步之前花费大量时间使某一步完美是没有意义的。**计划迭代：**

*   对于大型规范（Specification），先只编写规范的一部分，继续测试并实现该部分，然后通过更完整的规范进行迭代。

*   对于复杂的测试套件（Test suite），先选择几个重要的划分（Partitioning），并为它们创建小型测试套件（Test suite）。继续通过简单的实现（Implementation）来通过这些测试，然后在测试套件（Test suite）中迭代更多的划分（Partitioning）。

*   对于棘手的实现（Implementation），首先编写一个简单的暴力实现（Implementation）来测试你的规范（Specification）并验证（Validation）你的测试套件（Test suite）。然后自信地转向更难的实现（Implementation），因为此时你的规范（Specification）是好的，测试也是正确的。

迭代是每个现代软件工程流程（例如 [敏捷开发（Agile）](https://en.wikipedia.org/wiki/Agile_software_development) 和 [Scrum 框架（Scrum）](https://en.wikipedia.org/wiki/Scrum_(software_development))）的一个特征，并有良好的实证支持证明其有效性。迭代需要一种与你作为学生解决作业和考试题时习惯的不同心态。迭代意味着尽快达成一个粗略的解决方案，然后稳步细化和改进它，而不是试图从头到尾完美地解决问题，这样你就有时间在必要时丢弃并重做。当问题困难且解决方案空间未知时，迭代能最有效地利用你的时间。

> **背景扩展：** 在学校做作业时，我们通常追求“一次做对”；但在工程实践中，需求和技术细节往往随探索而清晰，迭代允许我们在早期犯错并以低成本修正。就像雕塑家先凿出粗胚再精雕细琢，而非直接刻画细节。

总结
-------------------------------------------------------------------------

在本次阅读中，我们看到了这些理念：

*   测试优先编程（Test-first programming）。在编写代码之前先编写测试。
*   使用划分（Partitioning）和边界值（Boundary）进行系统化测试，以设计正确、全面且小巧的测试套件（Test suite）。
*   白盒测试（Glass box testing）和语句覆盖率（Coverage）用于补充测试套件。
*   尽可能隔离地对每个模块进行单元测试（Unit test）。
*   自动化回归测试（Regression testing）以防止缺陷重现。
*   迭代式开发（Iterative development）。计划重做某些工作。

今日阅读的主题与我们好软件的三个关键属性联系如下：

*   **远离缺陷（Safe from bugs）。** 测试是为了发现代码中的缺陷，而测试优先编程是为了尽可能早地发现它们，就在引入缺陷之后。

*   **易于理解（Easy to understand）。** 使用文档化的测试策略进行系统化测试，使得理解测试用例是如何选择的以及测试套件有多全面变得更容易。

*   **准备变更（Ready for change）。** 正确的测试套件仅依赖于规范中的行为，这允许实现在规范 confines 内变更。我们还讨论了自动化回归测试，这有助于在对代码进行更改时防止缺陷重现。

> **学习批注：** 这三个属性是软件工程的核心目标。测试套件作为“可执行的规范”，不仅保护代码免受回归缺陷的影响，还记录了模块的预期行为，使得其他开发者更容易理解和安全地修改代码。
