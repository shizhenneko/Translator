版本控制系统的发明
-------------------------------------------------------------------------------------------

[版本控制系统](http://en.wikipedia.org/wiki/Revision_control)是软件工程领域必不可少的工具。几乎每一个项目——无论是严肃的还是业余的，开源的还是专有的——都会使用版本控制。如果没有版本控制，协调一个团队的程序员同时编辑同一个项目的代码，会带来令人抓狂的烦恼。

> **学习批注：** 这里用“抓狂的烦恼”来形象地比喻没有版本控制时团队协作的混乱局面，强调了版本控制的必要性。

Git
-------------------------------------------------------------------------------------------

当今最流行的版本控制系统是 Git。Git 最初由 Linus Torvalds 于 2005 年为 Linux 内核开发而创建，如今已成为事实上的标准。

Git 对象图
-------------------------------------------------------------------------------------------

Git 将其版本历史存储为一个有向无环图（DAG）的数据结构。理解这个图对于掌握 Git 至关重要。

Git 操作
-------------------------------------------------------------------------------------------

基本的 Git 工作流程通常包括以下步骤：
1.  **修改**工作目录中的文件。
2.  **暂存**（`git add`）更改，为提交做准备。
3.  **提交**（`git commit`）更改，创建一个永久的历史快照。
4.  **推送**（`git push`）或**拉取（pull）**（`git pull`）更改，与远程仓库同步。

版本控制与“三大特性”
-------------------------------------------------------------------------------------------

版本控制直接支持软件工程中追求的三大特性：
1.  **安全性**：历史记录可恢复，避免灾难性数据丢失。
2.  **并发性**：多人可同时工作，系统帮助合并更改。
3.  **可追溯性**：可以追踪每个更改的作者、时间和原因。

发明版本控制
---------------------------------------------------------------------------------------------------------------------

假设 [Alice](http://en.wikipedia.org/wiki/Alice_and_Bob) 正在独自完成一个习题集。

Alice 版本 1 `hello.ts`

她从习题集中的一个文件 `hello.ts` 开始，并为此工作了几天。

在她需要提交习题集进行评分的最后一刻，她意识到自己做的某个更改破坏了一切。要是她能回到过去并找回一个旧版本就好了！

一个简单的保存备份文件的规程就可以完成这项工作。

> **学习批注：** 这里描述了一个最基本的版本管理方法——手动创建文件副本并命名。这是一种最原始但有效的“时光机”思路，核心需求是能够回溯到某个稳定或正确的时间点。

Alice 版本 1 `hello.1.ts` 版本 2 `hello.2.ts` 版本 3 `hello.ts` HEAD

Alice 根据自己的判断决定何时达到了一个值得保存代码的里程碑。她将 `hello.ts` 的版本保存为 `hello.1.ts`、`hello.2.ts` 和 `hello.ts`。她遵循一个惯例：最新的版本就叫 `hello.ts`。我们将最新的版本称为 _头（HEAD）_。

现在，当 Alice 意识到版本 3 存在致命缺陷时，她只需将版本 2 复制回她当前代码的位置。灾难避免了！但如果版本 3 中包含一些好的更改和一些坏的更改怎么办？Alice 可以手动比较文件以找出更改，并将它们分为好的和坏的更改。然后，她可以将好的更改复制到版本 2 中。

> **背景扩展：** 这种手动“挑出”好更改的过程实际上就是软件工程中的“拣选（cherry-pick）”操作的原型。它非常繁琐且容易出错，尤其是在更改量大的时候。

这需要大量工作，而且人眼很容易漏掉更改。幸运的是，有一些标准的软件工具可用于比较文本；在 UNIX 世界中，其中一个工具是 [`diff`](http://en.wikipedia.org/wiki/Diff)。一个更好的版本控制（version control）系统将使生成差异（diff）变得容易。

云存储 版本 1 `hello.1.ts` 版本 2 `hello.2.ts` 版本 3 `hello.ts`
Alice 版本 1 `hello.1.ts` 版本 2 `hello.2.ts` 版本 3 `hello.ts`

Alice 还想为她的笔记本电脑被公交车碾压的情况做好准备，因此她将工作的备份保存在云端，每当她对工作目录（working directory）的内容感到满意时，就上传其内容。

如果她的笔记本电脑被压扁，Alice 可以取回备份，并在一台新机器上恢复习题集的工作，同时保留随时“时光旅行”回到旧版本的能力。

此外，她可以在多台机器上开发她的习题集，将云服务提供商作为一个共同的交换点。Alice 在笔记本电脑上做了一些更改，并将它们上传到云端。然后她在家里的台式机上下载，做更多的工作，并将改进后的代码（包含旧文件版本）上传回云端。

> **学习批注：** 这里的云存储充当了“中央服务器”或“远程仓库”的角色，是现代分布式版本控制系统（如 Git）中“远程（remote）”概念的雏形。它实现了在不同设备间同步整个项目历史。

云存储
版本 5L `hello.ts` Alice 在笔记本电脑上 Alice 在台式机上 版本 5D `hello.ts`

然而，如果 Alice 不小心，这种方法可能会遇到麻烦。想象一下，她开始在笔记本电脑上编辑 `hello.ts` 以创建“版本 5”。然后她分心了，忘记了她的更改。后来，她在台式机上开始开发一个新的“版本 5”，其中包含了*不同的*改进。我们将这些版本称为“5L”和“5D”，分别代表“笔记本电脑”和“台式机”。

当需要将更改上传到云端时，就有可能发生事故！Alice 可能会将她所有的本地文件复制到云端，导致云端只包含版本 5D。之后 Alice 从云端同步到她的笔记本电脑，可能会覆盖版本 5L，从而丢失有价值的更改。Alice 真正想要的是在这里进行*合并（merge）*，以基于这两个版本 5 创建一个新版本。

> **背景扩展：** 这个场景生动地展示了在没有同步机制的情况下进行并行修改会导致的“覆盖”问题。现代版本控制系统通过检测历史分叉（fork）并引导用户进行合并来解决这个问题。

至此，仅考虑一个程序员独自工作的场景，我们已经得出一个版本控制方案应该支持的操作列表：

*   *回退（reverting）*到过去的版本
*   *比较（comparing）*两个不同的版本
*   *推送（pushing）*完整的版本历史到另一个位置
*   *拉取（pulling）*该位置的历史记录
*   *合并（merging）*源自同一早期版本的不同分支版本

仅仅上传新的源文件并不是向他人传达一组更改背后高级思想的很好的方式。因此，让我们添加一个日志，为每个版本记录**谁**编写了它、**何时**最终确定、以及**更改内容是什么**（以简短的人工编写消息形式）。

现在，推送另一个版本变得稍微复杂一些，因为我们需要合并（merge）日志。这比处理 TypeScript 文件更容易，因为日志结构更简单——但如果没有工具支持，爱丽丝和鲍勃将需要手动完成！我们还想强制执行日志与实际可用文件集之间的一致性：对于每个日志条目，应该能够轻松提取该条目创建时处于当前状态的一组完整文件。

但是有了日志，各种有用的操作就成为可能。我们可以查看仅针对特定文件的日志：即限制为涉及修改某个文件的那些更改的日志视图。我们还可以使用日志来找出每行代码是由哪个更改贡献的，或者更好的是，由哪个人贡献的，这样当代码不工作时我们就知道该向谁抱怨。这类操作手动执行会非常繁琐；版本控制（version control）系统中自动化的操作被称为**注解**（annotate），或者不幸地，也被称为**追责**（blame）。

> **学习批注：** 这里的“合并日志”是版本控制协作中的关键步骤。想象一下你和朋友共同编辑一份在线文档，你们各自在本地做了修改并添加了说明。当你们都试图保存时，系统需要将你们的两条编辑记录（日志）合理地整合成一条时间线，而不是简单地覆盖。这类似于合并日志的概念。
> 
> **背景扩展：** `annotate`（或`blame`）命令是版本控制中一个强大的代码审查和溯源工具。虽然“blame”这个名字听起来有些负面，但它在实际开发中主要用于理解代码历史和定位问题引入的上下文，是团队协作和代码维护的得力助手。
### 多个分支

有时让一部分开发者开辟一个**分支（branch）**进行工作是有意义的——这是一个并行的代码宇宙，例如用于实验新功能。其他开发者可能不希望在新功能完成前拉取这些更改，即使在此期间会创建多个协调版本。即使是单个开发者，也会发现创建分支很有用，原因与爱丽丝最初独自工作时仍使用云端服务器类似。

一般来说，拥有多个用于交换项目状态的共享位置会很有用。可能同时存在多个分支位置，每个位置由若干程序员共享。通过适当的设置，任何程序员都可以从任何位置**拉取（pull）**或向任何位置**推送（push）**，从而在协作模式上实现极大的灵活性。### 令人震惊的结论

当然，事实证明我们在这里并没有发明任何新东西：[Git](http://git-scm.com/) 已经为你完成了所有这些事情，许多其他版本控制（version control）系统也是如此。### 分布式 vs 集中式

传统的**集中式**版本控制系统，例如 [CVS](https://www.nongnu.org/cvs/) 和 [Subversion](http://subversion.apache.org/)，实现了我们上面设想的部分功能。它们支持一个具有一个主服务器（primary server）的协作图（collaboration graph）——即谁与谁共享了什么更改——而副本只与主服务器通信。

> **背景扩展：** 集中式版本控制（centralized version control）的一个核心特征是存在一个单一的权威数据源（主服务器），所有用户都直接与之同步。这简化了“最新版本”的定义，但引入了单点故障风险。

在一个集中式系统中，每个人都必须与主仓库（primary repository）共享和获取工作。只有当更改**在主仓库中**时，才算是被**安全地存储在版本控制中**，因为那是唯一的仓库。

爱丽丝 鲍勃

相反，像 [Git](http://git-scm.com/) 和 [Mercurial](https://www.mercurial-scm.org/) 这样的**分布式**版本控制系统则允许各种不同的协作图，团队或子团队可以轻松地试验代码和历史的替代版本，并在确定是好的想法时将不同版本合并在一起。

> **学习批注：** 分布式版本控制（distributed version control）的核心是每个开发者都拥有完整的仓库副本，包括完整的历史记录。这使得离线工作、分支创建和实验变得非常高效，但同时也要求团队明确定义工作流程（例如，什么是“官方”版本）。

在一个分布式系统中，所有仓库（repository）都是平等的，由用户来为它们分配不同的角色。不同的用户可能与不同的仓库共享和获取工作，团队必须自行决定什么意味着一个更改**处于版本控制之下**。一个程序员仓库中的更改是否需要先与指定的协作者或服务器共享，然后团队其他成员才认为它是正式的？#### 阅读练习

查看解释### 版本控制（version control）术语

*   **仓库（Repository）**：存储我们项目各个版本的本地或远程位置
*   **工作副本（Working copy）**：我们可以在其上工作的、可编辑的本地项目副本
*   **文件（File）**：我们项目中的一个单独文件
*   **版本（Version）**或**修订版（revision）**：在某个时间点我们项目内容的记录
*   **更改（Change）**或**差异（diff）**：两个版本之间的区别
*   **HEAD**：当前的版本

> **学习批注：** 了解这些核心术语是使用任何版本控制系统的基础。你可以把**仓库（Repository）**想象成一个项目的时光机档案库，它保存了所有历史快照。**HEAD** 是一个特殊指针，它总是指向你当前正在查看或基于其工作的那个版本（通常是某个分支上的最新提交）。
### 版本控制系统的特征

*   **可靠**：能长期保存版本；允许备份
*   **多文件**：跟踪整个项目的版本，而非单个文件
*   **有意义的版本**：记录变更内容及原因
*   **回退**：恢复旧版本，可以是全部或部分恢复
*   **比较版本**：查看具体发生了哪些变化
*   **查看历史记录**：查看整个项目或单个文件的历史
*   **不仅限于代码**：也适用于散文、图片……

它应该**允许多人协同工作**：

*   **合并（merge）**：整合从一个共同祖先版本分叉出来的不同版本
*   **追踪责任**：记录是谁做出了更改，谁修改了哪行代码？
*   **并行工作**：允许程序员独立工作一段时间（同时仍享有版本控制）
*   **共享进行中的工作**：允许多个程序员共享未完成的工作（既不影响他人，也不放弃版本控制）

Git 项目的历史是一个 [**有向无环图**](http://en.wikipedia.org/wiki/Directed_acyclic_graph) （DAG）。这个历史图是存储在 `.git` 中的完整对象图的骨干，所以让我们先关注它一下。

![Image 10](https://web.mit.edu/6.031/www/sp22/classes/05-version-control/figures/hello-git-history.png)

历史图中的每个节点都是项目的一个**提交（commit）**，也称为**版本（version）**或**修订版（revision）**：它代表了项目在那个时间点上所有文件的完整快照。你可能从 [之前的阅读材料](https://web.mit.edu/6.031/www/sp22/getting-started/#getting_the_history_of_the_repository) 中记得，每个提交都由一个唯一的 ID 标识，显示为一个十六进制数。

除了初始提交外，每个提交都有一个指向其**父提交（parent commit）** 的指针。例如，提交 `1255f4e` 的父提交是 `41c4b8f`：这意味着 `41c4b8f` 先发生，然后是 `1255f4e`。

> **学习批注：** 理解父提交的概念很重要。它建立了提交之间的链式关系，代表了版本历史的演进路径。每个提交（除第一个外）都基于其父提交的状态创建。

有些提交拥有相同的父提交。这些是项目从某个共同的先前版本分叉出来的不同版本，例如，可能是因为两个开发者在独立工作。

> **背景扩展：** 想象两个开发者 Alice 和 Bob，他们都在某个时间点从版本 X 签出了项目副本。Alice 随后创建了提交 A，Bob 创建了提交 B。那么 A 和 B 都指向 X 作为它们的父提交。这就在历史图中创建了一个分支。

而一个提交可以有两个父提交。这是一个将分叉的历史重新结合起来的版本，例如，因为那些开发者随后将他们各自的工作再次合并到了一起。

> **学习批注：** 这就是合并提交（merge commit）。当 Git 将两个分支的更改整合在一起时，它会创建一个新的合并提交，这个提交有两个父提交，分别指向被合并的两个分支的最新提交。上面示例图中的 `3e62e60` 就是一个合并提交。

分支——记住 `main` 目前将是我们唯一的分支——只是一个指向某个提交的名称。

最后，HEAD 指向我们当前的提交——几乎是这样。我们还需要记住我们正在哪个分支上工作。所以，HEAD 指向当前分支，而当前分支指向当前提交。

> **学习批注：** 把 HEAD 想象成一个“你在这里”的标记。它告诉你当前工作目录和下一次提交的基础对应的是哪个提交。在大多数情况下，HEAD 指向一个分支名，该分支指向一个具体的提交。

检查解释### 序列、树和图

当你独立在一台机器上工作时，版本历史的有向无环图（DAG）通常看起来像一条序列：提交 1 是提交 2 的父节点，提交 2 又是提交 3 的父节点……

在我们的示例仓库历史中，涉及三位程序员。其中两位——Alyssa 和 Ben——"同时"进行了修改。这里的"同时"并非指时间上完全重合，而是指他们基于同一个_先前_版本创建了两个不同的_新_版本，正如[Alice 在她的笔记本电脑和台式机上分别创建了版本 5L 和 5D](https://web.mit.edu/6.031/www/sp22/classes/05-version-control/#version_5L_5D)一样。

当多个提交共享同一个父提交时，我们的历史 DAG 就从序列变成了树：它分叉了。请注意，项目历史中的分支并不需要任何人特意创建一个新的 Git 分支，仅仅意味着我们从同一个提交开始，在仓库的不同副本上并行工作：

⋮
*   commit 82e049e248c63289b8a935ce71b130a74dc04152
|   Author: Ben Bitdiddle <ben.bitdiddle@example.com>
|   Greeting in Ruby
|     
| * commit 64009369c5ab93492931ad07962ee81bda921ded
|/  Author: Alyssa P. Hacker <alyssa.p.hacker@example.com>
|   Greeting in Scheme
|  
* commit 1255f4e4a5836501c022deb337fda3f8800b02e4
| Author: Max Goldman <maxg@mit.edu>
| Change the greeting
⋮

最后，当分叉的变更被合并到一起时，历史 DAG 就从树形变成了图状：

⋮
*   commit 3e62e60a7b4a0c262cd8eb4308ac3e5a1e94d839
|\  Author: Max Goldman <maxg@mit.edu>
| | Merge
| |   
* | commit 82e049e248c63289b8a935ce71b130a74dc04152

| | Greeting in Ruby
| |   
| * commit 64009369c5ab93492931ad07962ee81bda921ded

> **学习批注：** 这里的序列、树、图描述了版本历史拓扑结构的变化。可以类比写文章：单独写作是线性的（序列）；你和朋友各自基于初稿改写，产生了两个版本（树）；最后把你们两个的改动整合到一篇文章里（图）。`Merge` 提交就是那个整合的节点。

变更如何被合并到一起呢？首先我们需要理解历史在不同用户和仓库之间是如何共享的。

通过 `git push` 和 `git pull` 发送与接收对象图
---------------------------------------------------------------------------------------------------------------------------------------------------------------------------

我们可以使用 **`git push`** 将新提交发送到远程仓库（remote repository）：

`git push origin main`

悬停或点击每个步骤以更新图表：

1.   当我们克隆（clone）一个仓库时，我们获得了历史图的一个副本。
     Git 会记住我们克隆的来源，并将其作为一个**远程仓库（remote repository）**，命名为 **`origin`**。
2.   使用 `git commit`，我们在 `main` 分支上向本地历史添加新的提交。
3.   为了将这些变更发送回 `origin` 远程，使用 `git push origin main`。

![Image 19](https://web.mit.edu/6.031/www/sp22/classes/05-version-control/figures/hello-git-push-0.png)

而我们使用 **`git pull`** 来接收新的提交。除了获取对象图的新部分，`git pull` 还会通过检出（check out）最新版本来更新工作副本（working copy）（就像最初 `git clone` 检出一个工作副本一样）。如果远程仓库和本地仓库都发生了变更，`git pull` 会尝试将这些变更合并到一起。

> **背景扩展：** `push` 和 `pull` 是同步本地与远程仓库的核心操作。`push` 是"上传"你的工作成果，`pull` 是"下载并整合"他人的工作成果。这就像团队共享一个云文档：你先从云端获取最新版（pull），编辑完自己的部分后，再上传保存（push）。

合并（Merge）
---------------------------------------------------------------------------------

让我们看看当变更并行发生时会发生什么：

并行创建并提交 `hello.scm` 和 `hello.rb`

悬停或点击每个步骤以更新图表：

1.   Alyssa 和 Ben 都**克隆**了包含两个提交（`41c4b8f` 和 `1255f4e`）的仓库。
2.   Alyssa 创建了 `hello.scm` 并将她的变更**提交**为 `6400936`。
3.   同时，Ben 创建了 `hello.rb` 并将他的变更**提交**为 `82e049e`。
     此时，他们两人的变更都只存在于各自的本地仓库中。在每个仓库里，`main` 现在指向了不同的提交。
4.   假设 Alyssa 率先将她的变更**推送**到了远程。
5.   如果 Ben 现在尝试推送会发生什么？推送会被拒绝：如果服务器将 `main` 更新为指向 Ben 的提交，那么 Alyssa 的提交就会从项目历史中消失！
6.   Ben 必须将他的变更与 Alyssa 的变更**合并**。
     为了执行合并，他先从远程**拉取**她的提交，这会做两件事：
     (a) 将新的提交下载到 Ben 仓库的对象图中
7.   (b) 将 Ben 的历史与 Alyssa 的历史合并，创建一个新的提交（`3e62e60`），它将两条历史连接在一起。这个提交和其他提交一样是一个快照：一个应用了他们两人所有变更的仓库快照。
8.   现在 Ben 可以 `git push` 了，因为这样做不会导致任何历史记录丢失。
9.   而 Alyssa 可以 `git pull` 来获取 Ben 的工作成果。

![Image 20](https://web.mit.edu/6.031/www/sp22/classes/05-version-control/figures/hello-git-merge-0.png)

> **学习批注：** 这个流程展示了典型的团队协作模式。Ben 的推送被拒绝是因为远程分支的"指针"已经前进（被 Alyssa 推上去了），他本地的历史已经落后。`pull` 操作实际上是 `fetch`（获取）加 `merge`（合并）的组合，它先把别人的改动拉下来，然后尝试与本地改动合并，生成一个新的合并提交后，整个历史线就汇合了，此时再推送就不会冲突。

在这个例子中，Git 能够自动合并 Alyssa 和 Ben 的变更，因为他们各自修改了不同的文件。如果他们两人都编辑了_相同文件的相同部分_，Git 就会报告一个**合并冲突（merge conflict）**。Ben 将不得不手动将他们的变更交织在一起，然后再提交合并结果。所有这些都在[入门指南中关于合并、合并操作以及合并冲突的部分](https://web.mit.edu/6.031/www/sp22/getting-started/#merges)有详细讨论。#### 阅读练习

为什么提交（commit）看起来像差异（diff）？
--------------------------------------------------------------------------------------------------------------------------------

我们已经将提交（commit）定义为我们整个项目在某个时间点的快照（snapshot），但如果你询问 Git，它似乎并不这么看：

$ git show 1255f4e
commit 1255f4e4a5836501c022deb337fda3f8800b02e4
Author: Max Goldman <maxg@mit.edu>
Date:   Mon Sep 14 14:58:40 2015 -0400

    更改问候语

diff --git a/hello.txt b/hello.txt
index c1106ab..3462165 100644
--- a/hello.txt
+++ b/hello.txt
@@ -1 +1 @@
-Hello, version control!
+Hello again, version control!

> **学习批注：** Git 默认显示提交之间的差异（diff），而不是完整的文件内容。这是因为在大多数提交中，只有一小部分文件被修改，显示差异更便于理解更改内容。这是一种空间优化和用户体验的权衡。

Git 假设我们的项目在大多数提交中大部分内容不会改变，因此只显示差异（diff）会更有用。绝大多数情况下，确实如此。

但我们可以让 Git 显示特定提交时仓库中的内容：

$ git show 3e62e60:
tree 3e62e60:

hello.rb
hello.scm
hello.txt

是的，仅仅添加一个 `:` 就完全改变了该命令的含义。

我们还可以查看该提交中特定文件的内容：

$ git show 3e62e60:hello.scm
(display "Hello, version control!")

> **背景扩展：** 这是一种简单的灾难恢复方法。如果你不小心破坏了文件，可以使用 `git show <commit>:<file>` 命令查看该文件在历史某个正常版本中的内容，然后复制出来进行修复。这体现了版本控制（version control）作为“时间机器”的价值。

这是你可以使用 Git 从灾难中恢复的最简单方法之一：让 Git `git show` 某个早期版本中现在已损坏文件在当时完好的内容。

我们将在课堂上练习一些灾难恢复命令。

版本控制（version control）与三大理念
-------------------------------------------------------------------------------------------------------------------------------------

版本控制（version control）如何与 6.031 的三大理念相关联？

**免受错误（Safe from bugs）**
*   查找某个功能何时何地被破坏
*   寻找其他类似的错误
*   增强代码未意外更改的信心

**易于理解（Easy to understand）**
*   为什么要进行某项更改？
*   同时还有哪些其他更改？
*   我可以向谁询问这段代码？

**便于更改（Ready for change）**
*   完全是关于管理和组织更改
*   回退未按计划工作的更改
*   接受并整合来自其他开发者的更改
*   在分支上隔离实验性工作

> **学习批注：** 版本控制（version control）系统不仅是代码备份工具，更是支撑软件工程核心原则的基础设施。它通过记录历史（便于追踪和回滚）、管理并行修改（通过分支和合并）以及促进协作，直接服务于代码的可靠性、可理解性和可维护性。
