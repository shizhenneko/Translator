## Outline
### Introduction
- Summary
  - Specifications act as contracts between implementers and clients.
  - They enable safe delegation and independent code evolution.
- Key takeaways
  - Always write specs before implementation or client code.
### Behavioral Equivalence
- Summary
  - Two functions are equivalent if clients cannot observe differences.
  - Equivalence depends on the advertised specification, not implementation.
- Key takeaways
  - Specify only what clients need; leave room for optimization.
### Specification Structure
- Summary
  - Precondition: client obligation (requires clause).
  - Postcondition: implementer obligation (effects clause).
- Key takeaways
  - If precondition fails, postcondition is void.
### TypeScript Specifications
- Summary
  - Use TypeDoc @param and @returns for human-readable contracts.
  - Static types cover part of the contract; the rest must be documented.
- Key takeaways
  - Keep specs in comments right above the function signature.
### Avoid null
- Summary
  - Disallow null by default; use union types sparingly.
  - Enable strict null checks to catch issues at compile time.
- Key takeaways
  - Prefer empty arrays/strings over null.
### Testing and Specifications
- Summary
  - Black-box tests rely only on specs; glass-box tests still obey specs.
  - Unit tests should fail only when the tested spec is violated.
- Key takeaways
  - Never write tests that depend on stronger guarantees than the spec.
### Mutating Functions
- Summary
  - Document side effects explicitly in the effects clause.
  - Mutation is forbidden unless stated otherwise.
- Key takeaways
  - Specify aliasing restrictions to avoid infinite loops or crashes.
### Exceptions
- Summary
  - Use @throws only for anticipated, recoverable failures.
  - Do not list bugs like TypeError in the spec.
- Key takeaways
  - Convert preconditions to postconditions with exceptions when useful.
### Special Results
- Summary
  - Return union types (e.g., T | undefined) instead of throwing for expected problems.
  - undefined is preferred over null when strict checks are on.
- Key takeaways
  - Let the type system remind callers to handle special cases.
### Summary
- Summary
  - Specs decouple modules, reduce bugs, and clarify intent.
  - Good specs are short, complete, and enforceable.
- Key takeaways
  - Write specs early, review them often, and enforce them with tests and types.

[行为等价（behavioral equivalence）](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#behavioral_equivalence)

[假设您正在维护一个程序，其中包含下面这个用于查找整数在数组中索引的函数：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@suppose_you_working)

```ts
function find(arr: Array<number>, val: number): number {
    for (let i = 0; i < arr.length; i++) {
        if (arr[i] === val) return i;
    }
    return -1;
}
```


[该 `find` 函数在程序中有许多客户端（client）（即调用该函数的地方）。现在您发现，当程序里用很大的数组调用 `find` 时，要查找的值往往要么靠近数组开头（很快就能找到），要么靠近末尾（会很慢，因为几乎要遍历整个数组）。于是您灵机一动，想出一个从两端同时搜索的加速方案：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@find_function_many)

```ts
function find(arr: Array<number>, val: number): number {
    for (let i = 0, j = arr.length-1; i <= j; i++, j--) {
        if (arr[i] === val) return i;
        if (arr[j] === val) return j;
    }
    return -1;
}
```


[能否放心地用新实现替换 `find`？我们会不会因此引入 bug？为了判断二者是否行为等价（behavioral equivalence），关键在于能否把一个实现无缝替换成另一个。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@safe_replace_find)

[不仅性能特征不同，这两个实现在输入/输出行为上也有差异：如果 `val` 在数组中**出现多次**，原 `find` 总是返回最小索引；而新 `find` 可能返回最小索引，也可能返回最大索引，取决于哪一端先找到。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@not_only_do)

[但当 `val` 在数组中恰好只出现一次时，两个实现的表现完全一致：都会返回该索引。很可能客户端并不关心其他情况——每次调用时，它们传入的数组都只有单个元素与 `val` 相等。对于这样的客户端，这两个 `find` 版本毫无差别，可以放心切换。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@but_val_occurs)

[行为等价这一概念“仁者见仁”——取决于客户端。为了能够在实现之间自由替换，并知道何时替换是安全的，我们需要一份**规范（specification）**，明确列出客户端依赖哪些行为。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@notion_behavioral_equivalence)

[在本例中，一份允许这两种实现行为等价的规范可能是：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@case_specification_would)

```ts
find(arr: Array<number>, val: number): number
```
requires:`val` 在 `arr` 中恰好出现一次
effects:返回索引 `i`，使得 `arr[i]` = `val`

> **学习批注：**
> 规范就像契约：前置条件（requires）是客户端必须满足的义务；后置条件（effects）则是实现必须兑现的承诺。只要双方都遵守契约，就能安全替换实现。

规范对函数实现者也有好处：它们赋予实现者无需通知客户端即可更改实现的自由。规范还能让代码更快。我们将看到，规范可以排除某些调用状态，这种对输入的限制可能让实现者跳过原本昂贵的检查，从而采用更高效的实现。

这份契约充当客户端与实现者之间的“防火墙”。它把客户端与模块的**内部实现细节**隔离开：作为客户端，您无需阅读源码，只要看规范即可。同时，它也将实现者与模块的**使用细节**隔离开：作为实现者，您无需询问每位客户端打算如何使用模块。这种防火墙带来**解耦**，使模块代码与客户端代码可以独立变更，只要双方都遵守规范——各自履行义务。

规范结构
----------------------------------------------------------------------------------------------------------------

抽象地说，函数的**规范（specification）** 包含几部分：

*   函数签名：给出名称、参数类型与返回类型
*   **requires** 子句：描述对参数的额外限制
*   **effects** 子句：描述返回值、异常及其他副作用

![Image 3](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/figures/firewall-implies.svg)
![Image 4](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/figures/firewall-unsat.svg)

这些部分共同构成函数的**前置条件（precondition）**与**后置条件（postcondition）**。

前置条件是客户端（函数调用者）的义务，是函数被调用时状态的约束。其一部分体现在函数签名的参数个数与类型上，额外条件写入 **requires** 子句，例如：

*   缩小参数类型（如 `x is an integer >= 0` 表示 `number` 参数 `x` 必须为非负整数）
*   参数间关系（如 `val` 在 `arr` 中恰好出现一次）

后置条件是函数实现者的义务，包含 TypeScript 可静态检查的部分（如返回类型），以及写入 **effects** 子句的额外条件，包括：

*   返回值与输入的关系
*   抛出的异常及触发条件
*   对象是否及如何被修改

总体而言，后置条件是在**假设前置条件于调用前成立**的前提下，对函数完成后程序状态的约束。

整体结构是一个逻辑蕴含：**若**调用时前置条件成立，**则**函数完成时后置条件必须成立。

如果调用时前置条件**不**成立，实现者**不受**后置条件约束。此时函数可任意行为：永不返回、抛出规范未提及的异常、返回任意结果、任意修改状态等。

[有些语言（尤其是 [Eiffel](http://en.wikipedia.org/wiki/Eiffel_(programming_language))）将前置条件（precondition）和后置条件（postcondition）作为语言的基本组成部分，运行时系统（甚至编译器）可以自动检查这些表达式，以强制客户端与实现者之间的契约。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@some_languages_notably)

[测试与规范（Testing and specifications）](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#testing_and_specifications)
----------------------------------------------------------------------------------------------------------------------

在测试中，我们区分**黑盒测试（black box tests）**——仅依据规范（specification）选择测试用例，以及**白盒测试（glass box tests）**——在了解实际实现的基础上选择测试用例（参见[《Testing》](https://web.mit.edu/6.031/www/sp22/classes/03-testing/#black_box_and_glass_box_testing)）。但务必注意，**即便白盒测试也必须遵循规范**。您的实现可能提供比规范更强的保证，或在规范未定义（undefined）之处表现出特定行为，但测试用例不应依赖这些行为。测试用例必须是[正确的](https://web.mit.edu/6.031/www/sp22/classes/03-testing/#systematic_testing)，像任何其他客户端一样遵守契约。

> **学习批注：** 白盒测试的价值在于覆盖实现路径，而非“偷窥”内部行为来放宽断言。例如，若实现总是返回最小索引，测试仍只能验证“返回某个有效索引”，否则当实现变更时测试会误报失败。

例如，假设您正在测试如下 `find` 的规范，该规范与我们之前使用的略有不同：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@example_suppose_you)

```ts
find(arr: Array<number>, val: number): number
```

[requires: `val` 存在于 `arr`
effects: 返回索引 `i` 使得 `arr[i]` = `val`](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@requires_val_occurs_arr_effects_returns)

该规范具有强前置条件：要求必须能找到 `val`；同时后置条件（postcondition）较弱：若 `val` 在数组中出现多次，规范并未指明返回哪一个 `val` 的索引。即使您将 `find` 实现为总是返回最小索引，测试用例也不能假定这一具体行为：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@spec_strong_precondition)

```
let array = [7, 7, 7];
let i = find(array, 7);
assert.strictEqual(i, 0);  // bad test case: assumes too much, more than the postcondition promises
assert.strictEqual(array[i], 7);  // correct
```

同样，即便您将 `find` 实现为在找不到 `val` 时（合理地）抛出异常，而非返回某个误导性的任意索引，测试用例也不能假定该行为，因为测试不应违反前置条件去调用 `find()`。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@similarly_even_if)

> **背景扩展：** 这种“不越界”的测试理念保障了代码重构自由。只要替换的实现仍满足规范，原有测试就应继续通过，从而支持持续集成中的安全重构。

那么，白盒测试的意义何在？它意味着您尝试寻找新的测试用例以覆盖实现的不同路径，但仍以与实现无关的方式、依据规范来验证这些用例。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@so_does_glass)

> **背景扩展：** 单元测试（unit testing）强调“最小可测试单元”的独立性，通常是一个函数或类方法。它像给每个零件做体检，确保零件本身无缺陷，再组装成整机。

我们当时讨论了**单元测试**，即我们应该**独立地测试程序的每个模块**。良好的单元测试只聚焦于**单个规范（specification）**。我们的测试几乎总会依赖 JavaScript 库函数的规范，但针对我们编写的某个函数的单元测试不应因为**另一个**函数未满足其规范而失败。正如示例中所见，针对 `extract()` 的测试不应因 `load()` 未满足其后置条件（postcondition）而失败。

[良好的**集成测试**（integration tests）会组合使用多个模块，确保不同函数的规范彼此兼容：调用者与被调用者按对方期望传递与返回值。集成测试无法取代系统化设计的单元测试。以示例来说，如果我们仅通过调用 `index` 来测试 `extract`，就只能在**潜在输入空间的一小部分**上测试它：即那些 `load` 可能输出的输入。这样一来，我们为缺陷留下了藏身之处，当您在程序其他地方以不同目的使用 `extract`，或当 `load` 开始返回新格式文档时，这些缺陷就会跳出来。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@good_integration_tests)

### [测试总比不测好](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#testing_is_better_than_not_testing)

我们无法在违反前置条件时测试行为：例如，无法检查函数是快速失败还是在非法输入时返回垃圾值，因为**所有测试都必须遵循规范（specification）**。如果前置条件（precondition）是实现者可以合理检查的，那么通常值得修改规范：移除前置条件，并在后置条件（postcondition）中描述行为。我们将在下面讨论两种实现方式（[异常](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#exceptions)和[特殊结果](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#special_results)），并在下一篇阅读材料中深入探讨此类规范编写决策。

其次，观察前置条件。它指出 `array1` 不能与 `array2` 是同一对象。若尝试将数组元素添加到自身，函数行为是**未定义值（undefined）**。您可以轻易理解实现者为何施加此约束：它不太可能排除任何有用的应用场景，同时让实现更简单。规范允许一种简单实现：从 `array2` 取一个元素追加到 `array1`，然后继续处理 `array2` 的下一个元素，直到末尾。

若 `array1` 与 `array2` 是同一数组，该简单算法将不会终止，如右侧快照图所示——或者实际运行时会因数组对象过大耗尽内存而抛出内存错误。无论无限循环还是崩溃，都因前置条件而被规范允许。

> **学习批注：** 前置条件在此充当“护栏”，让实现者无需处理自引用追加的复杂情况，类似电梯门上的“禁止倚靠”。

下面是另一个突变函数示例：

```ts
sort(array: Array<string>): void
```
[requires:无
effects:将 `array` 排序，即对所有 0 ≤ `i`<`j`<`array.length` 满足 `array[i]` ≤ `array[j]`](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@requires_nothing_effects_puts_array_sorted)

以及一个不突变参数的函数示例：

```ts
toLowerCase(array: Array<string>): Array<string>
```
[requires:无
effects:返回新数组 `t`，长度与 `array` 相同，其中 `t[i]` = `array[i].toLowerCase()`](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@requires_nothing_effects_returns_new_array)

正如除非另有说明否则禁止 `null`，程序员也默认**除非另有说明否则禁止突变（mutation）**。`to­Lower­Case` 的规范可以在 _effects_ 中显式声明“数组未被修改”，但若后置条件未描述突变，我们即要求不修改输入。

[异常](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#exceptions)
--------------------------------------------------------------------------------------

既然我们在编写规范并考虑客户端如何使用函数，现在讨论如何以安全且易理解的方式处理**异常**情况。

由于**异常**是函数可能的输出，它可能必须在函数的后置条件中描述。异常可通过文档注释中的 `@throws` 子句记录。本节讨论何时在规范中包含异常，何时不包含。

> **背景扩展：** 在 TypeScript 中，异常通常用 `throws` 标签标注，类似 Java 的 `@throws`，帮助调用者明确捕获或继续传播。
### [用于报告错误的异常](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#exceptions_for_signaling_bugs)

[您可能在 Python 或 TypeScript 编程中已经见过一些**异常（exception）**。例如，在 Python 中：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@you-ve_probably_already)

* [当数组索引 `array[i]` 超出数组 `array` 的有效范围时，会抛出 `IndexError`](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@indexerror_thrown_array)
* 当字典查找 `dict[key]` 找不到匹配的键时，会抛出 `KeyError`
* 对于各种动态类型错误，例如尝试在 `None` 上调用方法，会抛出 `TypeError`

[TypeScript 也有 `TypeError` 用于动态类型错误，但大多数动态错误通过一个通用的 `Error` 类来发出信号。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@typescript_also_typeerror)

[这类异常通常表明存在**错误（bug）**——无论是在客户端还是在实现中——并且异常抛出时显示的信息可以帮助您找到并修复该错误。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@these_kinds_exceptions)

[用于报告错误的异常不属于函数的后置条件（postcondition），因此它们不应出现在 `@throws` 中。例如，`TypeError` 通常绝不应在规约中被提及。参数的类型是前置条件（precondition）的一部分，这意味着一旦前置条件被违反，有效的实现可以在没有任何警告的情况下抛出 `TypeError`（例如，如果客户端设法传递了一个 null 值）。因此，下面这个规约示例就从未提及 `TypeError`：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@exceptions_signal_bugs)

```ts
/**
 * @param array array of strings to convert to lower case
 * @returns new array t, same length as array, 
 *         where t[i] is array[i] converted to lowercase for all valid indices i
 */
function toLowerCase(array: Array<string>): Array<string>
```


> **学习批注：**
> 异常若用于“防错”，则不应写进规约；规约只描述“正常路径”的后置条件。
> 例：`sqrt(x)` 规约只承诺 `x≥0` 时返回平方根，不承诺 `x<0` 时抛 `IllegalArgumentException`；后者是防御式实现细节。
### [应对预期失败的异常](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#exceptions_for_anticipated_failures)

[异常不仅用于报告程序错误，也可用于通知**可预期的失败源**，使调用者能够捕获并处理。此类异常应通过 `@throws` 子句记录，说明触发该失败的条件。例如：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@exceptions_not_just)

```ts
/**
 * Compute the integer square root.
 * @param x integer value to take square root of
 * @returns square root of x
 * @throws NotPerfectSquareError if x is not a perfect square
 */
function integerSquareRoot(x: number): number
```


[下面是 `addAll` 的新版规约：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@here-s_new_version)

```ts
/**
 * If the array1 !== array2, adds the elements of array2 to the end of array1.
 * @returns true if array1 changed as a result
 * @throws AliasingError if array1 === array2
 */
function addAll(array1: Array<string>, array2: Array<string>): boolean
```


> **学习批注：** 原版将 `array1 !== array2` 作为**前置条件（precondition）**，违反时行为**未定义值（undefined）**；新版去掉该前置条件，改用**后置条件（postcondition）**同时规约“数组不同”与“数组相同”两种情形，让调用者无需预判即可安全使用。

[在[上文原始 `addAll`](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#specifications_for_mutating_functions)中，规约把 `array1 !== array2` 列为前置条件：若违反，函数行为未定义。新版规约移除此前置条件，转而用后置条件同时定义“数组为不同对象”（“添加元素…”及 `@returns` 子句）与“数组为同一对象”（`@throws` 子句）两种情况的行为。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@original_addall_above)

[特殊结果](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#special_results)
------------------------------------------------------------------------------------------------

[异常（exception）是传达“调用者不太可能处理的问题”的最佳方式，例如调用者提供了非法输入：要么是调用者本身，要么是其上游调用者存在缺陷。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@exceptions_best_way)

[对于调用者理应准备处理的预期失败，不同编程语言采取不同策略。例如，在 Java 语言中，实现者可声明受检异常，调用者必须在静态层面处理：若不捕获该异常，也不将其加入自身规范（specification）的 `throws` 列表，编译器会给出静态错误。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@anticipated_failures_caller)

[TypeScript 不提供异常处理的静态检查，因此用异常处理预期失败容易成为缺陷源头。例如，假设我们用 `integerSquareRoot` 处理来自文件或用户输入的数据，却忘记对 `NotPerfect­Square­Error` 进行 `try ... catch`。非法数字将导致程序崩溃，而更好的做法是给出清晰错误提示或引导用户重试；然而静态检查无法提前暴露该问题。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@typescript_does_not_provide_static_checking)

[一种良好替代方案是将函数返回类型设为[联合类型（union type）](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html#union-types)，其值集是两个（或多个）其他类型值集的并集：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@good_alternative_make)


```ts
/**
 * Compute the integer square root.
 * @param x integer value to take square root of
 * @returns square root of x if x is a perfect square, undefined otherwise
 */
function integerSquareRoot(x: number): number|undefined
```

[`undefined` 与 `null` 非常相似：在 JavaScript 中，声明但未初始化的变量值为 `undefined`，而非 `null`。若未开启[严格空值检查（strict null checks）](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#avoid_null)，任何变量都可能为 `undefined` 或 `null`。开启严格检查后，二者均被排除。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@undefined_very_similar)

[按照惯例，`null` 表示“一个无意义的值”，应始终避免使用；`undefined` 表示“此处确实无值”，只要开启严格空值检查，我们即可将其用于联合类型以标识特殊情况。在示例中，若使用更新后的 `integerSquareRoot` 时未考虑其可能返回 `undefined`，多数情况下将产生静态错误：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@convention_null_used)


```ts
let twice = integerSquareRoot(input) * 2; // static error
if (integerSquareRoot(input) > 4) { ... } // static error
```

[… 尽管如此，我们仍需保持谨慎：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@although_must_still)


```ts
console.log('Your lucky number is:', integerSquareRoot(5)); // no error
```


> **学习批注：**
> 在 TypeScript 中，用 `undefined` 而非 `null` 表达“无结果”可使编译器在严格空值检查下强制您处理该情况，减少运行时崩溃。
### [缺失的 `Map` 键](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#missing_map_keys)

[如果您有一个 Python 字典，当尝试查找其中不存在的键时会发生什么？](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@if_you_python)

```python
zoo = { 'Tim': 'beaver' }
zoo['Tim']     # => 'beaver'
zoo['Bao Bao'] # => raises KeyError: 'Bao Bao'
```


[Python 会将其视为异常。TypeScript 做出了不同的选择：](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@python_considers_exception)

```ts
const zoo = new Map([['Tim', 'beaver']]);
zoo.get('Tim');     // => 'beaver'
zoo.get('Bao Bao'); // => undefined
```


> **学习批注：** 在 Python 中，访问不存在的键会抛出 `KeyError`；而 TypeScript 的索引签名默认返回 `undefined`，这是两种语言在“安全性 vs 便利性”权衡上的差异。

[在 Python 中，后置条件（postcondition）规定了一个 `KeyError`。在 TypeScript 中，对于键类型为 `K` 的 `Map`，后置条件规定返回类型为 `K|undefined`。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@python_postcondition_specifies)
### [非法数组索引](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#illegal_array_indices)

[如果我们把动物园保存在数组而不是映射中会怎样？](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@if_keep_our)

```ts
const zoo = [ 'Tim' ];
for (let i = 0; i <= 1; i++) {
  let name: string = zoo[i];
  console.log(`Hello, ${name}!`);
}
// => prints:
//    Hello, Tim!
//    Hello, undefined!
```

> **学习批注：** 当数组索引越界时，TypeScript 默认返回 `undefined`，这会导致类型系统出现“漏洞”。开启 `noUncheckedIndexedAccess` 后，索引访问结果会变为 `T | undefined`，迫使您显式处理非法索引情况。

[糟糕。编译器允许将 `zoo[i]` 赋值给 `name`，尽管 `name` 必须是 `string`，而 `zoo[i]` 可能并不是！这是静态类型系统的又一个漏洞，需要另一项 TypeScript 配置：开启 _no unchecked index access_ 后，`[..]` 索引运算符的返回类型将变为与 `undefined` 的联合类型。到目前为止，在 6.031 中该选项都是关闭的。我们将在后续练习和作业中开启它。一旦开启，我们就必须在类似代码中考虑索引可能非法的情况，或者修改代码以避免使用索引。](https://web.mit.edu/6.031/www/sp22/classes/06-specifications/#@oh_no_compiler)
